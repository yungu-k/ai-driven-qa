AI-Native를 목표로 삼고 달려온 지 반년이 넘었다. 그동안 실무의 QA 파이프라인을 내가 얼마나 바꿨는지 궁금해져서 회고를 해 봤다. 방법은 단순하다. 3년 전의 업무 방식과 지금의 업무 방식을 같은 순서로 적고 나란히 놓았다.

결과부터 말하면, 일부 엣지 케이스 수행과 E2E 시나리오 테스트를 빼면 거의 모든 단계를 AI가 대신하고 있다. 물론 판단과 의사결정이 필요한 부분은 여전히 내가 한다.

## 3년 전과 지금

프로젝트 하나가 킥오프부터 Sign-off까지 가는 순서대로 적었다. 그 단계를 어떻게 바꿨는지 따로 쓴 글이 있으면 마지막 칸에 이어 두었다.

| 단계 | 3년 전 | 지금 | 자세히 |
|---|---|---|---|
| 킥오프 | QA로서 준비할 것들을 메모해 챙긴다 | 준비는 같다. 메모는 AI가 구조화된 문서로 정리해 준다 | |
| 기획 리뷰 | 품질이나 테스트에 관한 질의응답 (정적인 QA 활동) | 리뷰 방식은 같다. 뒤의 Test Case 설계를 위해 AI에게 기획서를 읽혀 둔다 | |
| QA Plan | 기획서를 바탕으로 세워 문서로 쓰고 유관 부서에 공유 | AI가 기획서를 바탕으로 쓰고 사람이 검토 | |
| Test Case 설계 | 사람이 설계 | AI가 기획서를 보고 쓴다. 기준은 내가 설계해 둔 마크다운(md) 파일 | [디자인 시안에서 TC 600개까지](/posts/tc-design-automation/) |
| 개발 완료 시점 | Mock 데이터나 Mock 서버를 미리 준비하고 Sanity Test | AI가 코드 변경분(diff)을 보고 Test Case를 다시 검토. 자동화 테스트 스크립트도 이때 작성 | [티켓 산문 대신 코드 diff를 읽는다](/posts/diff-driven-tc/) |
| Test Case 수행 | 사람이 수행 | E2E 시나리오 테스트와 일부 엣지 케이스를 빼면 자동화 테스트가 맡는다 | |
| 버그 리포팅 | 사람이 리포팅 | AI가 코드를 분석해 추정 원인과 함께 Jira에 등록 | |
| Status Report | 사람이 써서 유관 부서에 공유 | AI가 쓴다 | |
| Regression Test | 모든 버그가 고쳐진 뒤 사람이 수행 | 자동화 테스트가 대신한다 | |
| Sign-off | 사람이 진행하고 QA Report도 사람이 쓴다 | 사람이 진행하고 리포트는 AI가 쓴다 | [데이터에서 PDF까지, 사람은 서명만 한다](/posts/qa-report-automation/) |
| 자동화 테스트 | 서비스가 어느 정도 안정되면 구축 | 자동화 테스트 스크립트를 업데이트 | |

## 가장 크게 바뀐 것

표에서 가장 많이 움직인 칸은 세 곳이다.

첫째는 Test Case 설계다. 예전에는 기획서를 바탕으로 내가 설계했다. 지금은 AI가 기획서를 보고 쓰고, 나는 AI가 따를 기준을 md 파일로 설계해 둔다. 내 손이 가는 곳이 Test Case에서 그 기준 문서로 옮겨 갔다.

둘째는 개발이 끝난 직후다. 예전에는 이 시점에 Mock을 준비하고 Sanity Test를 했다. 지금은 AI가 코드 변경분을 보고 Test Case를 다시 검토하고, 자동화 테스트 스크립트도 이때 같이 작성된다. 3년 전에는 서비스가 안정된 뒤에야 자동화 테스트를 구축했다. 지금은 그 시점이 개발이 끝나는 순간으로 당겨졌다.

셋째는 버그 리포팅이다. 테스트하다 버그가 나오면 AI가 코드를 분석해서 추정 원인과 함께 Jira에 등록한다.

## 아직 내가 하는 것

판단과 의사결정이 필요한 부분은 여전히 내가 한다. AI가 쓴 QA Plan은 사람이 검토하고, QA Sign-off도 사람이 진행한다. 수행 쪽에서는 E2E 시나리오 테스트와 일부 엣지 케이스가 남아 있다.

## 다음 단계는 공통 문서다

여기서 더 나아가려면 기획·개발·QA 담당자가 쓰는 AI가 업무마다 공통된 문서를 바라보고 있는 게 중요하다. 다른 조직도 마찬가지다. 여기서 공통 문서는 메인이 되는 기획서, 특정 Confluence 문서, Jira 티켓 같은 것들이다.

이 공통 문서를 수정하고 관리하는 규칙을 정하고, 그 규칙을 완벽하게 통제할 수 있다면 AI-Native에 한 걸음 더 가까워지지 않을까 생각한다. 코드가 바뀌면 기획서가 따라오게 만든 시도는 [멈춘 기획서를 소스 코드에서 다시 뽑았다](/posts/plan-from-source-pipeline/)에 적었다.

## 이미 그렇게 바뀐 곳, 리포트

AI 시대 이전에는 QA 엔지니어가 QA Report에 많은 리소스를 쏟았다. 나도 그랬다. 그런데 요즘 리포트를 만드는 비용은 "0"에 수렴한다. AI 에이전트가 다 만들어 주기 때문이다.

이제 리포트는 사람 품이 드는 업무가 아니다. 그때그때 뽑는 일회성 결과물이다. 사람이 관리할 대상은 따로 있다. 업무 중에 남기는 원본 기록(Raw)과, 계속 관리되는 운영 문서다.

그래서 「효과적인 리포트를 쓰려면 데이터를 어떻게 관리해야 하는가」에서 생각을 시작했다. 그리고 이 관점으로 내가 실무에서 검토하고 구현했다.

QA Report에 무엇이 필요한지부터 따져 보면 이렇다.

- Jira에 있는 데이터
- Test Case 정보와 케이스별 특이사항 코멘트
- 테스트 결과 데이터
- 이 모두를 종합한 결론. 즉 사람의 판단(Opinion)

Opinion을 뺀 나머지는 모두 MCP 연동으로 끌어올 수 있다. MCP(Model Context Protocol)는 AI가 Jira 같은 외부 도구를 직접 읽게 해 주는 연결 방식이다. 리포트의 구조를 잡는 일도 md 파일에 미리 정의해 둘 수 있다. 내가 QA Report를 쓰는 방식은 [qa-spec-kit의 QA_REPORT.md](https://github.com/yungu-k/qa-spec-kit/blob/main/QA_REPORT.md)에 공개해 두었다.

사람이 관리하는 것은 원본 기록과 리포트 규격 문서이고, 리포트는 그 위에서 AI가 뽑는다. 앞에서 말한 공통 문서가 리포트에서는 이미 이렇게 돌아가고 있다.

## 오늘도

나는 오늘도 AI-Native를 위해 고민하고, 조직 안의 사람들과 논의하는 중이다.
