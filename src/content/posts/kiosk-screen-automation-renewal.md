## 화면 트랙 — 이 글이 다루는 범위

카지노 키오스크는 두 종류다. 손님이 현금을 넣으면 칩을 내주는 기기, 칩을 넣으면 현금이나 전자지갑 잔액으로 바꿔 주는 기기. 돈과 칩이 실제로 오가는 기계라 검증도 두 갈래로 나뉜다 — 기기 제어 프로그램과 서버가 정해진 대로 주고받는지 보는 **장비·서버 트랙**, 그리고 손님이 보는 화면이 정해진 대로 움직이는지 보는 **화면 트랙**. 이 글은 화면 트랙 이야기다. (두 트랙 인프라 전체는 [키오스크 자동화 인프라](/posts/kiosk-automation-infra)에 있다.)

화면 트랙이 답하는 질문은 하나다: **"이 응답이 오면 화면이 이렇게 움직이는가."** 벨트가 실제로 돌았는지, 지폐가 실제로 나왔는지는 답하지 않는다 — 그건 장비 검증의 몫이고, 이 경계를 흐리면 어느 쪽도 책임지지 않는 회색지대가 생긴다.

검사의 구성도 인프라 글 시점과 달라졌다. 당시의 "128"은 화면별 공통 검사를 설계 계산(32화면 × 4종)으로 센 수치다. 지금 그 계열은 활성 화면 30개 기준 114건이다 — 화면 2개는 검사하지 않는데, 하나는 스펙 밖이고 하나는 어떤 화면도 그 주소로 보내지 않는 도달 불가 화면이다. 도달 못 하는 화면은 검사가 통과해도 보장하는 것이 없다. 여기에 화면 단위로는 잡히지 않는 **거래 흐름 검사 119건**이 더해져, 전체 233건(통과 221 + 의도적 제외 12)이 돈다.

이번 리뉴얼에서 바뀐 건 두 가지다. "실물 장비가 없으면 못 한다"며 몇 달째 사람 몫으로 묶여 있던 26건 중 25건이 자동화로 넘어왔고 — 그렇게 커진 자동화에서 **초록이 거짓말할 수 있는 경로 여섯 개**를 찾아 막았다. 이 글은 그 두 이야기다.

## "실물이 없으면 못 한다"는 대부분 틀렸다

26개 항목이 "실물 칩이 필요하다, 물리 센서라 안 된다, 실제 배출을 봐야 한다"는 이유로 사람 몫에 묶여 있었다. 몇 달째 그대로였다. 전환점은 한 문장이었다.

> "정상 상황 외 에러 상황들에 대해서도 응답을 받아서 실제 에러 화면이 잘 뜬다면 통과로 보면 되는 거잖아."

맞는 말이었다. **화면을 가르는 것은 실물이 아니라, 장비가 돌려주는 응답과 기기 설정이다.** 손이 감지됐다는 응답이 오면 화면은 셔터를 다시 연다 — 실제 손이 있었는지는 화면이 알지 못한다. 전수 재검토해 25건을 옮겼다.

| 묶음 | 화면을 가르는 것 |
| --- | --- |
| 칩 투입·인식 9건 | 칩이 있나 / 닫아도 되나 / 무엇이 몇 개 인식됐나 |
| 카드 로그인 분기 4건 | 회원 등급, 카드 사용 가능 여부, 비밀번호 판정 결과 |
| 현금 배출·회수 3건 | 배출구에 지폐가 남았나 + 대기 시간 설정 |
| 칩 이송 2건 | 이송 시간 설정에서 계산되는 분할값 |
| 현금·거래완료 7건 | 투입구 잔류 여부 + 무동작 복귀 시간 설정 |

남긴 1건이 오히려 기준을 증명한다. 현금 투입 기기의 "미회수 현금 자동 회수"는 화면이 회수를 지시하지 않는다 — 대기 시간이 지나면 화면은 그냥 첫 화면으로 돌아가고, 지폐를 끌어들이는 건 기계가 스스로 한다. **화면에서 관측할 신호가 없다.** 반면 칩 교환 기기는 화면이 회수를 직접 지시하므로 자동화했다. 같은 "미회수 회수"인데 두 기기의 답이 갈린다 — 기준이 "실물이냐"가 아니라 **"화면에 신호가 남는가"**이기 때문이다.

분류의 사유는 낡는다. "왜 안 되는지"를 적어 두지 않으면 아무도 다시 안 따진다.

## 초록이 거짓말하는 경로들

자동화가 커지면 초록도 커진다. 문제는, 통과가 늘 진실은 아니라는 것. 리뉴얼 중에 세 사건을 겪었다 — 전부 제품 결함이 아니라 **자동화 쪽 결함**이었다.

### 사건 1 — 검사값이 실물과 달랐다

검사는 통과하고 있었는데, 검사하던 숫자가 실제 기기 값이 아니었다. 화면에 먹이는 기기 설정 기본값이 **앱에 들어 있던 개발 편의용 임시값(테스트 스텁)을 그대로 베낀 것**이었고, 실제 기기 설정과 5개 항목이 달랐다. 가장 문제였던 건 1회 거래 한도 — 실제보다 작은 임시값으로 계산해 "최대 장수를 넣으면 한도에 걸린다"는 잘못된 결론까지 냈다. 자동화는 그 잘못된 결론에 맞춰 초록이었다.

이걸 자동화가 잡지 못했다. **사람이 잡았다.**

> "1회 거래 한도가 그 값이라고? 무슨 근거로? 실제 한도는 다른데?"

고치는 방식은 사람 기억에 의존하지 않게 — 실제 기기 설정을 직접 읽어 검사값과 대조하는 **설정 대조기**를 만들었다. 지금은 어긋나면 즉시 실패한다. 만들자마자 누락된 항목 하나를 더 잡아냈다. 값의 출처 규칙도 문서로 못박았다:

| 값의 종류 | 정본 | 베끼면 안 되는 것 |
| --- | --- | --- |
| 기기 설정 (한도·권종·대기시간) | 실제 관리 서버 응답 | 앱의 개발용 임시값 |
| 장비 응답 | 실제 장비 응답 기록 | 앱의 흉내내기 응답 |
| 화면 문구 | 문구 파일 | 기억·추측 |
| 화면 분기 조건 | 화면 소스의 실제 비교식 | "대충 0 아니면 실패겠지" |

```js
// ❌ 숫자를 박으면 설정이 바뀔 때 조용히 딴 것을 검사한다
const 최대장수 = 100;

// ✅ 기기 설정에서 끌어온다
const 최대장수 = Number(기기설정.한번에받는장수[0]);
const 금액한도 = Number(기기설정.거래한도[0]);
const 넣을장수 = Math.min(최대장수, Math.floor(금액한도 / 권종));
```

통과율은 품질 지표가 아니다. **무엇을 상대로 통과했는지**가 지표다. 개발 편의용 임시값은 스펙이 아니다 — 편하게 쓰이다가 조용히 정본이 된다.

### 사건 2 — 통과를 판정하는 도구 자체가 틀려 있었다

실행 결과를 테스트 케이스 문서에 자동 반영하는 기능을 만들었다. 그런데 실패를 찾는 조건이 테스트 실행기가 주는 실제 결과값과 **다른 어휘**였다. 실패가 하나도 잡히지 않았다 — 무엇을 돌려도 전부 통과로 적혔을 것이다.

잡은 방법은 단순했다. 만든 직후 **일부러 결과를 실패로 바꿔 넣어** 잡히는지 확인했고, 안 잡혔다. 통과를 판정하는 코드는 초록만 보고는 검증할 수 없다 — 빨강을 넣어 봐야 한다. 판정 규칙도 후하지 않게 다시 정했다:

```js
function 판정(결과들) {
  if (결과들.some(r => r === "실패"))       return "FAIL";
  if (결과들.some(r => r === "재시도통과")) return "불안정";   // PASS 로 덮지 않는다
  if (결과들.every(r => r === "건너뜀"))    return "N/T";
  if (결과들.some(r => !아는값(r)))         return "확인필요"; // 조용히 통과시키지 않는다
  return "PASS";
}
```

재시도해서 통과한 것(불안정)은 통과로 덮지 않는다 — 한 번에 통과하지 못한 검사는 신호로 쓸 수 없다. 모르는 결과값이 오면 "확인 필요"로 표시한다 — 판정 규칙이 낡았다는 신호이기 때문이다. 조용한 통과 대신 사람이 확인하는 비용을 택했다.

문서에 적히는 초록도 두 종류를 구분한다. 검사 이름에 케이스 번호가 있어 결과를 그대로 받는 **직결 109건**, 번호 없이 그 화면 검사 전체의 통과 여부로 판정하는 **화면 판정 6건** — 근거의 강도가 다른 두 초록을 같게 보이게 하면 안 되니까, 어느 쪽인지 함께 적는다.

검사 도구의 버그는 제품 버그보다 위험하다. **없는 안심을 만들어 낸다.**

### 사건 3 — 그 초록이 어느 빌드의 것인지 몰랐다

관리 화면은 두 기기 앱이 모두 "꺼짐"이라고 표시했다. 실제로는 이틀 전에 띄운 앱 두 개가 멀쩡히 돌고 있었다. 그 상태에서 [기동]을 누르니 "포트가 이미 사용 중"으로 죽었다. 진짜 문제는 포트가 아니었다 — **그날 나온 221건 통과가 어느 빌드에서 나온 것인지 알 수 없었다.** 결과는 남았는데 대상이 안 남았다.

원인은 수명 차이다. 키오스크 앱은 검증 서버가 띄우지만 서버보다 오래 산다. 서버를 재기동하면 관리 코드는 프로세스 손잡이를 잃고 초기값("꺼짐")으로 되돌아가는데, 앱은 그대로 돈다. 고친 방식: 포트를 쥔 프로세스를 찾아 **실행 인자에서 어떤 빌드인지 직접 읽어 이어받는다.** 읽지 못하면 "꺼짐"이 아니라 "실행 중 (무엇인지 확인 불가)"라고 말한다.

> 모르는 것을 "꺼짐"이라고 말하는 것이 가장 나쁘다. 모른다고 말해야 사람이 확인한다.

실행 버튼 위에는 「지금 검증하는 대상」을 항상 표시하고, 결과에는 대상 버전을 네 곳(결과 파일 · 요약 · 테스트 케이스 문서 · 실행 이력)에 남긴다. 검증 결과는 **대상이 특정돼야 근거가 된다** — 대상이 빠지면 리포트로도, 회귀 판단으로도 못 쓴다.

### 나머지 경로들 — 부수 실패 기록

| 무엇 | 배운 것 |
| --- | --- |
| 응답 가로채기 우선순위 — 브라우저 자동화 도구는 나중에 등록한 규칙이 이긴다. 넓은 규칙이 좁은 규칙을 덮어 응답이 통째로 비었고, 한 세션에서 네 번 물렸다 | 도구의 규칙 순서는 외우는 게 아니라 한 번 당하고 적어 두는 것 |
| 개발용 흉내내기 응답이 목록을 배열이 아니라 문자열로 반환 — 화면이 그 자리에서 죽었다. 실제 장비는 배열을 준다 | 흉내가 실물과 다르면 그 위의 검증은 의미가 없다 |
| 문서화된 케이스 2건이 소스에 존재하지 않는 동작을 기대 | **없는 동작에 붙은 테스트는 통과해도 보장하는 것이 없다** |

## 일부러 자동화하지 않은 것

검증 대상 빌드는 계속 올라온다. 사람이 매번 받아다 올리면 결국 낡은 것을 검증하게 되니, 최신 빌드를 자동으로 받아 두게 만들었다. **그런데 거기서 멈췄다.** 받아 두기만 하고 기동은 하지 않는다. 처음엔 선택 기본값이 최신으로 자동 점프하게 만들었는데, 이것도 되돌렸다.

이유는 회귀 신호다. 검증 기준이 저절로 따라 올라가면, 어제 초록이던 것이 오늘 빨개졌을 때 **제품이 깨진 건지 기준이 바뀐 건지 구분할 수 없다.** 편의를 얻는 대가로 회귀 신호가 죽는다 — 그 거래는 하지 않기로 했다.

| 일 | 누가 |
| --- | --- |
| 새 빌드 받아오기 | 자동 (주기적, 「새 버전 N개」 알림까지만) |
| 무엇을 기준으로 검증할지 | **사람** (화면에서 선택해 고정 — 재기동에도 유지) |
| 기동 | 사람 |

자동화의 성숙도는 무엇을 자동화했는지가 아니라 **무엇을 자동화하지 않았는지**에서 드러난다.

## 남은 것

- **검사가 흉내 내는 장비 응답 가운데 11건은 아직 실제 응답과 대조하지 못했다** — 남아 있는 실제 기록이 장비 미연결 오류 응답뿐이라, 정상 응답의 형태를 댈 수 없기 때문이다. 이 공백은 숨기지 않고 문서에 남겨 뒀다. 숨기지 않는 것이 이 체계의 전제다.
- **다음은 검증 대상의 실제 빌드 버전을 앱이 스스로 알리게 하는 것.** 지금은 파일명·소스 커밋까지는 정확하지만 앱이 스스로 답하지는 않는다. 이게 되면 "무엇을 검증했나"가 완전해진다.
- 사람 몫으로 남은 1건은 화면 밖의 일이다 — 장비 트랙이 답할 영역이다.

> 검사 221건이 25.5분에 돈다. 하지만 이번 리뉴얼에서 배운 건 속도가 아니다 — 초록을 세는 것보다, 그 초록이 무엇을 상대로 나온 것인지 따지는 쪽이 QA의 일이라는 것.
