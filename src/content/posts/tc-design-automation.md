> Figma 시안을 분석해 Google Sheets에 TC를 자동 생성하는 핵심 워크플로우. 규격 문서 하나만 있으면 어떤 프로젝트에서든 같은 품질의 TC가 나온다.

## 시안은 봤는데, 옮겨 적는 게 일이다

새 화면 시안이 나오면 QA는 그걸 테스트 케이스로 번역한다. 화면 하나에 약 10행(체감치) — 정상 경로, 예외, 경계, 상태 전이를 뽑아 쓰고, 그 위에 Priority·드롭다운·조건부 서식·테두리·틀 고정까지 손으로 입힌다. TC 내용을 짜는 것보다 시트를 사람이 볼 수 있는 문서로 만드는 서식 노동이 시간을 더 먹는 날도 많았다. 이 글은 그 반복을 규격 문서 하나로 걷어낸 과정을 다룬다 — 무엇을 자동화했고, 어디까지는 사람 몫으로 남겼는지까지.

문제는 이게 창의적인 일이 아니라는 거다. 시안의 구조는 이미 Figma 안에 데이터로 다 있다. 서식 규칙도 매번 같다. 사람이 반복해서 옮기고 칠하고 있을 뿐이다.

## 접근 — 규격이 정본, AI는 실행기

핵심 결정은 "AI에게 TC를 잘 짜달라고 부탁하지 않는다"였다. 대신 **TC 설계 표준을 규격 문서로 정의**하고(컬럼 구성, Priority 정책, 서식 순서까지), AI는 그 규격을 Figma 시안에 적용해 시트에 직접 쓰는 실행기로 뒀다. 품질의 원천은 프롬프트가 아니라 규격이다 — 규격이 정밀하면 산출물이 정밀하고, 규격이 모호하면 AI도 모호하게 쓴다.

Figma 분석은 하이브리드 2단계로 잡았다. 메타데이터(노드 트리)만 읽으면 UI 텍스트가 `title`, `description` 같은 제네릭 이름으로 나와 구체적인 TC를 못 쓴다. 반대로 스크린샷만 보면 hidden 노드 필터링이나 구조 완전성을 보장 못 한다. 그래서 메타데이터로 구조·순서를 확보하고, 텍스트가 제네릭한 핵심 화면만 골라 스크린샷으로 보완한다.

## 구현 — 분석 → 규격 적용 → 서식까지

**① 하이브리드 분석 + 분기 파싱.** 메타데이터로 화면 구조를 잡고 hidden 노드·비-UI 프레임(메모·설명)을 걸러낸다. 여기에 규칙 하나를 더 박았다 — 화면 옆의 `Description` 주석 프레임에 적힌 **비즈니스 분기(예외 조건, 진입 케이스, 상태 전이별 메시지)를 개별 TC로 분할 의무화**. 이 규칙이 없을 땐 "비-UI 프레임 필터링"에 분기 로직까지 같이 걸러져 TC가 통째로 누락됐다.

**② Full TC + Smoke TC 2시트 자동 생성.** 전수 검증용 Full과 빠른 확인용 Smoke를 한 번에 만든다.

**③ 서식은 9단계 체크리스트로 고정.** 서식이 매번 빠지거나 순서가 꼬여 깨지는 걸 막으려고, 적용 순서를 규격에 못박았다. 요지만 옮기면:

```
데이터 입력 → 폰트(IBM Plex Sans) → 병합 →
컬럼 너비(px 실값) → 드롭다운(Data Validation) →
Priority 조건부 서식 → 틀 고정(Freeze) → … →
Border는 반드시 맨 마지막, 그리고 채워진 영역에만
```

- **드롭다운 값**은 대소문자까지 고정한다(`Pass`/`Fail`/`N/A`/`N/T` — `PASS`는 불가). 
- **Border는 맨 마지막**에, 그것도 데이터가 채워진 영역에만 그린다. 전체 범위에 일괄로 그으면 빈 요약 영역·구분선까지 테두리가 생겨 산출물이 지저분해진다.

## 시행착오 — 규칙과 한계를 몸으로 배웠다

**1. 서식이 매번 빠지거나 덮어써졌다.** 데이터만 넣고 서식을 빠뜨리거나, 적용 순서가 틀려 뒤 단계가 테두리를 덮어썼다. → 9단계 체크리스트로 순서를 고정. 특히 Border는 마지막 단계로 못박아 해결.

**2. 드롭다운 칩 색상의 API 한계.** Google Sheets API로는 드롭다운 칩(둥근 pill)의 색상을 못 넣는다. 조건부 서식으로 우회해봤지만 버렸다 — 칩 스타일이 깨져서 얻는 것보다 잃는 게 컸다. 결론: 드롭다운만 API로 넣고 색상은 자동화하지 않고 수동 영역으로 명확히 분리. API 한계는 빨리 인정하는 게 시간을 아낀다.

**3. TC를 사람으로 가르려 했던 정책을, 다시 버렸다.** 한동안 TC를 "주니어 수행 가능 / 시니어 협업 / 보류" 3분류로 나누고 행 배경색까지 칠했다. 그런데 곧 깨달았다 — **TC를 사람 등급으로 나누면 안 된다.** 모든 TC는 그 자체로 따라 수행 가능해야(Step 자기완결성) 한다. 그래서 3분류 정책을 폐기하고, 대신 이렇게 바꿨다:

- ⓐ 스텝을 자기완결적으로 쓴다.
- ⓑ 자원·권한 의존은 사전조건에 사실로 명시하고, 스텝에 `(개발자)` 라벨을 단다.
- ⓒ 지금 검증 불가한 건 결과를 `N/T`(Not Tested, 미수행)로 두고 사유를 적는다.

"설계자가 아는 걸 수행자도 안다"고 가정하지 않기 — 이 블로그에서 반복해 다루는 [지식의 저주](/posts/ai-confirmation-bias-subagents)와 같은 교훈이다.

## 결과

- 이 워크플로우로 3개 이상 프로젝트에서 누적 600개 이상의 TC를 작성했다. 손으로 쓰면 하루 100건 남짓이니, 600개는 대략 6일치 작성 노동에 해당한다.
- 대표 시안 1세트를 TC로 옮기는 데 **수동 5일이 자동 2~3시간으로** 줄었다(검토 시간은 별도이고, 정식 병행 비교가 아니라 경험치다). 서식 노동이 사라진 게 큰 몫이다.
- 규격 문서만 있으면 프로젝트가 바뀌어도 동일 품질이 나온다. 품질을 사람의 컨디션이 아니라 문서로 보장하게 됐다.

| | 수동 | 규격 자동 |
| --- | --- | --- |
| 시안 1세트 → TC | 약 5일 | 2~3시간 (검토 별도) |
| 서식 | 손으로 9단계 입력 | 규격대로 자동 |
| 품질 편차 | 사람 컨디션 의존 | 프로젝트 무관 동일 |

## 교훈

> 규격 문서의 품질이 곧 산출물의 품질이다. 서식 규칙을 '체크리스트'로 단계화하면 AI가 빠뜨리지 않는다.

- TC 작성 기준은 **"처음 보는 사람이 바로 따라 할 수 있는 수준"**으로 명시해야 한다. 추상적으로 쓰면 AI도 추상적으로 쓴다.
- **API 한계는 빨리 파악해 '수동 영역'으로 분리**하면 우회에 매달리는 시간이 줄어든다.
- 좋은 정책도 틀렸다 싶으면 버려라. TC를 사람 등급으로 가르던 규칙을 폐기한 게, 오히려 산출물을 더 튼튼하게 만들었다.
