> 전수 TC에서 Regression 스위트를 자동 추출하고, Jira 상태 변화를 TC 시트에 자동 동기화한다. (반대 방향 — TC의 Fail을 Jira 버그로 만드는 쪽은 [Bug Report 자동화](/posts/bug-report-automation)가 담당한다. 둘을 합치면 TC ↔ Jira 왕복이 닫힌다.)

## 릴리스마다 두 번 반복하는 손노동

릴리스가 돌 때마다 QA는 두 가지 반복 노동을 한다. 하나는 **전수 TC에서 이번에 돌릴 회귀 스위트를 다시 고르는 일**, 다른 하나는 **Jira 이슈 상태가 바뀔 때마다 TC 시트의 결과를 손으로 맞춰주는 일**이다.

둘 다 판단이 아니라 규칙에 가깝다. "Blocker급만 골라라", "완료된 티켓의 TC는 Pass로 바꿔라" 같은. 규칙이면 자동화할 수 있는데, 매 릴리스 사람이 손으로 하고 있었다. 그리고 손으로 하니 어긋났다 — 티켓은 완료인데 TC는 Fail로 남아 있는 식으로.

## 접근 — 추출 규칙과 상태 전이 규칙을 명문화

두 반복 모두 "규칙을 명확히 정의하면 자동으로 돈다"는 같은 구조였다.

- **회귀 추출**은 "P0만 뽑기"가 아니라 **"P0 + 플로우 보완"**으로 정의했다. Blocker TC만 떼어내면 그 앞 단계(로그인, 진입 등)가 빠져 테스트 자체가 수행 불가해진다. 그래서 P0를 뽑되, 플로우 완전성을 위해 필요한 선행 P1을 함께 채운다.
- **상태 동기화**는 Jira 상태 → TC 결과의 **전이 규칙을 표로 못박았다.** 모호한 규칙은 곧 데이터 불일치가 된다.

## 구현

**① Regression 스위트 자동 추출.** 전수 TC에서 다음 규칙으로 회귀 스위트를 뽑는다.

- P0(Blocker) 자동 추출 + 플로우 보완용 선행 P1 추가
- N/A(비대상) TC 제외
- 대분류에 소스 접두사 자동 부여
- 프로젝트 무관 — 어떤 TC 시트에든 동일 규칙 적용

이렇게 뽑힌 회귀 스위트는 현재 **120개 규모**로 유지된다. 전수를 다 돌릴 수 없는 릴리스 주기에서, "무엇을 꼭 다시 확인해야 하는가"를 사람의 기억이 아니라 규칙이 결정하게 됐다.

**② Jira → TC 상태 동기화.** 이슈 상태가 바뀌면 연결된 TC 결과를 규칙대로 되쓴다.

| Jira 상태 | TC 결과 | 조건 |
| :--- | :--- | :--- |
| 완료 | **Pass** | 연결된 **모든** 티켓이 완료일 때만 |
| 반려 | **N/A** | 재현 불가 / 요건 변경 |
| 수정됨 | **Fail 유지** | 검증 대기 (아직 확인 전) |
| 다시 열림 | **Fail 유지** | 재발 버그 |

핵심은 "완료 → Pass"에 붙은 **조건**이다. 하나의 TC에 여러 티켓이 걸려 있을 때, 일부만 완료됐다고 Pass로 넘기면 거짓 통과가 된다.

## 시행착오

**1. 다중 티켓 연결 TC.** 한 TC에 여러 티켓이 물려 있을 때, 그중 하나만 완료돼도 Pass로 바뀌는 버그가 있었다. → **"연결된 모든 티켓이 완료일 때만 Pass"** 규칙을 명시해 해결. 상태 전이에서 가장 조심할 지점이 이 "부분 완료"다.

**2. 운영자 관점과 사용자 관점의 혼동.** 관리자 화면은 운영자 전용인데, 동기화·서술 과정에서 사용자 관점 표현이 TC에 섞이곤 했다. → 관점 규칙을 피드백 메모리에 저장해 맥락을 고정했다. 한 번 짚어주면 끝날 것 같은 규칙도, 명시적으로 박아두지 않으면 반복해서 샌다.

## 결과

- 릴리스마다 손으로 고르던 회귀 선정이 **규칙 기반 자동 추출**로 바뀌어, **120개 규모의 스위트**를 사람의 기억 없이 일관되게 유지한다. 이 스위트 1바퀴 실행에 약 **2일**이 든다 — 매 릴리스 전수를 돌릴 수 없어 회귀를 규칙으로 좁혀 뽑는 이유다.
- Jira 상태 변화가 TC 시트에 자동 반영돼, **"티켓은 완료인데 TC는 Fail로 남는"** 이 유형의 어긋남을 그 뒤로 다시 보지 못했다.
- [Bug Report 자동화](/posts/bug-report-automation)와 합쳐, TC → 버그 → 상태 → TC의 **왕복이 닫혔다.**

| | 수동 | 규칙 자동 |
| --- | --- | --- |
| 회귀 선정 | 매 릴리스 손으로 P0 고름 | 규칙 기반 추출 (120건, 1바퀴 2일) |
| 상태 동기화 | 손으로 TC 결과 맞춤 | Jira 상태 → TC 자동 반영 |
| 어긋남 | 티켓 완료·TC Fail 잔존 | 이 유형을 그 뒤 다시 안 봄 |

## 교훈

> 상태 동기화에서 가장 중요한 건 '상태 전이 규칙'을 명확히 정의하는 것이다. 모호한 규칙은 곧 데이터 불일치다.

- Regression은 'P0만 추출'이 아니라 **'P0 + 플로우 보완'**이 실질적이다. 빠진 선행 단계가 있으면 테스트가 성립하지 않는다.
- "부분 완료" 같은 **엣지 조건을 규칙에 먼저 박아야** 자동화가 거짓 통과를 만들지 않는다.
