> 4월부터 QA 업무를 하나씩 AI로 자동화했다. TC 작성, 버그 등록, QA Report, 고친 버그의 TC를 Pass로 돌리는 일이 차례로 내 손을 떠났다. 그런데 이 자동화들은 대부분 내 PC에서만 돌았다. 그래서 QA 팀이 같이 쓰는 사내 웹 도구 하나로 모았다. 이름은 QA Hub다. 이제 QA 동료 누구나 TC 작성부터 Report까지 이 도구에서 할 수 있다. 내 PC에서는 AI가 낸 결과를 내가 눈으로 보고 리뷰 후 수정했다. QA Hub에서는 서버가 AI의 결과를 먼저 검사하고, 사람은 꼭 정해야 할 것만 정한다. 서버가 무엇을 어떻게 검사하는지는 아래에 기능마다 적었다.

올해 4월 첫 자동화 글을 쓴 뒤로 반년 넘게 QA Workflow를 AI와 함께 다시 설계했다. 하나의 Figma 기획 문서에서 TC를 작성하는 일은 5일에서 2~3시간으로 줄었다(TC 리뷰 시간 제외). 버그 한 건을 등록하는 일은 5분에서 1분 안쪽이 됐다. 메일 본문을 반나절 붙잡고 쓰던 QA Report는 PDF 한 벌로 바뀌었고, 테스트 결과를 Report로 만드는 데는 체감상 20분이 걸리지 않았다. 이 과정은 [반복은 스크립트, 판단은 AI, 결정은 사람](/posts/repetition-to-ai-judgment-to-human/)에 아홉 단계로 정리해 두었다.

자동화 대부분이 내 PC에서만 돌았다는 것은 이런 뜻이다. 화면 Regression Test를 돌리는 서버 하나만 예외였다. 나는 Claude Code에 Jira와 Google Sheets를 연결해 두었고, 규칙 문서는 내 폴더에 있었다. AI가 낸 결과는 내가 직접 읽어 본 뒤 시트에 올렸다. 같은 팀 QA 동료가 이것을 쓰려면 내 PC 설정을 통째로 옮겨야 했다. 결과를 확인하던 내 눈은 옮길 방법이 없었다.

이 글은 그 자동화들을 팀 웹 도구 하나로 모은 기록이다. 기능은 새로 만든 것이 거의 없다. 모두 최근 Release의 Sprint에서 실무에 이미 쓰던 것이다. 다만 스크립트와 명령으로 흩어져 있었다.

도구를 만든 것은 내 AI 팀원들이다. AI 팀원은 QA, 개발, 디자인 같은 역할을 하나씩 맡겨 둔 Claude Code 세션이고, 사람이 아니다. 나는 방향을 정하고 무엇을 남길지 골랐다. AI 팀원을 어떻게 꾸렸는지는 [AI 팀원 만들기](/series/ai-teammate/) 시리즈에 있다.

## 목차

## 혼자 쓰던 자동화가 여섯 개 쌓였다

QA Hub의 메뉴 여섯 개는 모두 이 블로그에 한 번씩 쓴 자동화에서 왔다.

| 먼저 쓴 글 | 그때 자동화한 일 | QA Hub 메뉴 |
| --- | --- | --- |
| [디자인 시안에서 TC 600개까지](/posts/tc-design-automation/) · [티켓 산문 대신 코드 diff를 읽는다](/posts/diff-driven-tc/) | 시안과 코드 변경을 읽고 규칙대로 TC 쓰기 | TC 작성 |
| [버그 한 건 쓰는 데 5분에서 1분으로](/posts/bug-report-automation/) | TC 행을 재료로 Jira 버그 쓰기 | Bug 등록 |
| [데이터에서 PDF까지, 사람은 서명만 한다](/posts/qa-report-automation/) | 시트와 Jira를 모아 Sign-off Report 만들기 | QA Report |
| [티켓은 완료인데 TC는 Fail](/posts/regression-and-status-sync/) | 버그가 닫히면 TC 결과를 Pass로 고치기 | Close 확인 |
| [600건 알람을 누락 0으로 분류하기](/posts/live-issue-triage/) | 운영 알람과 로그를 AI로 분류하기 | 로그 분석 |
| [테스트 1,160건으로 무인 키오스크를 지켰다](/posts/kiosk-automation-infra/) | 장비·서버 API와 화면을 자동 테스트로 지키기 | 자동화 결과 |

이 가운데 TC, 버그, Report, Close 확인 넷은 같은 방식으로 돌았다. 규칙은 md 파일에 적어 둔다. Claude Code가 그 규칙을 읽고, MCP나 API로 Jira와 시트를 다룬다. MCP는 AI가 Jira 같은 도구를 직접 다루게 해 주는 연결 방식이다. 결과는 내가 본다. 나 혼자일 때는 이 방식이 잘 돌았다. 규칙이 바뀌면 md 한 줄을 고치면 됐고, AI가 엉뚱한 결과를 내면 내가 바로 알아챘다.

최근 Release의 Sprint 내내 이 방식으로 TC를 쓰고, 버그를 올리고, 수정 확인 후 Fail을 Pass로 돌리고, Sign-off Report를 냈다. 실무에는 충분했다. 대신 하나하나가 따로 놀았다. Report가 가장 심했다. 이 Release에서 세 번의 Sprint를 진행했는데, Sprint마다 Report를 만드는 스크립트를 새로 짰다. 세 번째 Sprint의 Report는 만들기까지 16단계를 거쳤다. 그 사이사이에 내 일이 끼어 있었다. 시트 탭을 고르고, Jira에서 뽑은 결함 목록과 빌드 버전을 스크립트에 옮겨 적고, 문장을 다듬고, PDF를 쪽마다 눈으로 봤다. 그 Report는 아홉 번 다시 만들었다.

4월 글 제목처럼 「사람은 서명만 한다」였던 것은 처음 적용한 Release 하나에서였다. 돌아보면 아홉 번 다시 만든 것은 그때 Report 디자인을 새로 잡던 중이라, 형식이나 세부 내용이 마음에 들지 않을 때마다 다시 만들었기 때문이다. Report에 이렇게 손이 많이 가면 안 된다. 체계가 잡히면 한 번 만든 Report로 Reporting을 끝낼 수 있어야 한다.

QA Hub의 QA Report 메뉴는 이 일을 한 곳에 모았다. Sprint마다 새로 짜던 스크립트 대신 같은 생성 코드가 돈다. 사람은 작업 공간과 시트 탭을 고르고, 결함 목록은 서버가 Jira에서 직접 읽는다. 숫자와 표는 생성 코드가 계산한다. 디자인은 디자인 AI 팀원이 정해 둔 정본 서식 파일(CSS) 하나를 고치지 않고 그대로 쓴다. 빌드 버전과 판정 문장은 지금도 사람이 시트에 적는다. 자세한 것은 뒤의 「QA Report」 절에 적었다.

처음에 AI 팀원들에게 「우리 QA Hub 툴 하나 만들자.」로 시작하는 글을 보냈다. 웹 화면에서 다루게 하고, 나중에는 사내망에 올려 다른 사람들도 같이 쓰게 하겠다는 내용이었다. 그 글에는 「AI-Native 플랫폼이 될것임」이라는 줄도 있었다. 총괄을 맡은 AI 팀원이 새 저장소를 만들고, QA·개발·디자인 AI 팀원에게 일을 나눴다. 목표는 QA 동료들이 각자 자기 PC 브라우저로 접속해서, 내가 내 PC에서 하던 일을 버튼으로 하는 것이었다.

## 내 PC에서는 내가 검사기였다

자동화를 웹 도구로 옮기는 일은 화면을 씌우는 것으로 끝나지 않았다. 가장 크게 바뀐 것은 AI 결과를 누가 검사하느냐였다.

내 PC에서는 AI가 시트에 행을 쓰기 전에 내가 그 행을 읽었다. AI가 화면에 없는 버튼 이름을 지어내면, 나는 실제 화면을 떠올려 보고 그 줄을 지웠다. 팀 도구에서는 버튼을 누르는 사람이 결과를 나만큼 의심하지 않을 수 있다. 바쁜 날이면 나도 그렇다. 그래서 내가 하던 검사를 서버 코드로 옮겨야 했다.

QA Hub의 설계는 여기서 시작한다. **AI는 시트와 Jira에 직접 기록하지 않는다.** 파일도 만들거나 고치지 않는다. AI는 서버가 준 자료를 읽고, TC 초안 같은 결과를 정해진 스키마에 맞춘 JSON 답 하나로 낸다. 그 답을 시트와 Jira에 기록하는 일은 서버가 한다. 그것도 사람이 버튼을 누른 뒤에만 한다.

그림에서 점선 상자는 AI가 닿는 범위다. 그 상자에서 밖으로 나가는 것은 AI의 답 하나뿐이고, 그 답은 먼저 서버 검사로 간다.

### AI 호출 방식

서버는 AI를 Claude Code의 명령 한 줄(`claude -p`)로 부른다. 화면 없이 명령으로만 돌리는 방식이다. 작업마다 새로 띄우고, 쓸 수 있는 도구는 읽기 도구 셋(Read, Grep, Glob)으로 묶는다.

```bash
claude -p --restricted --strict-mcp-config --tools Read,Grep,Glob \
  --permission-mode dontAsk --no-session-persistence \
  --output-format stream-json --verbose \
  --json-schema "$(cat contract.json)"   # 기능마다 정해 둔 JSON 스키마
# 작업 폴더(jobs/<id>/work)에서 실행하고, 규칙과 지시는 표준 입력으로 넘긴다
```

AI는 Jira를 직접 읽지 않는다. 서버가 먼저 티켓, 첨부파일, 소스, 시트 행을 모아 작업 폴더에 파일로 둔다. AI는 그 폴더만 읽을 수 있다. 이렇게 하면 좋은 점이 셋 있다.

- AI에게 무엇을 줬는지 서버 기록으로 안다. AI가 「이걸 봤다」고 하는 말에 기대지 않아도 된다.
- 같은 자료로 다시 돌려 볼 수 있다.
- 티켓 본문에 누가 「이 파일을 지워라」 같은 지시를 적어 두어도 AI는 따를 수 없다. AI에게는 파일을 지우거나 고치는 도구가 없다.

폴더에 넣기 전에 서버는 사람 정보를 마스킹한다. 티켓의 작성자 칸을 빼고, 본문의 멘션, 계정 id, 이메일을 `<사람>` 같은 글자로 바꾼다. 소스에 든 비밀번호 같은 값도 마스킹한다. 마스킹한 뒤에도 남은 것이 보이면 그 파일은 통째로 뺀다.

규칙 문서도 요청이 올 때마다 파일에서 새로 읽어 AI에게 넘긴다. TC 규칙은 md 파일 세 개다. 어느 버전의 규칙을 넘겼는지는 작업 기록에 남는다. 규칙을 고칠 때는 서버를 다시 배포하지 않고 md 파일만 고친다. 4월 첫 자동화 때부터 규칙 문서를 먼저 쓰고 AI가 그것을 읽게 했는데, 그 방식을 그대로 이었다.

AI는 서버 전체에서 한 번에 한 건만 돈다. 앞에 작업이 있으면 기다려야 한다. 그래도 화면은 따로 돌아서, AI가 일하는 동안 다른 메뉴는 멈추지 않는다. 대기 목록은 누구나 볼 수 있다. 누가 어떤 티켓을 돌리는지 보여도 되냐는 물음에 나는 「내부망이라 투명하게 다 보여도 괜찮아」라고 답했다.

### 응답 스키마에 일부러 넣지 않은 것

AI의 답은 기능마다 정해 둔 JSON 스키마를 따라야 한다. 스키마에 맞는지는 두 번 본다. AI를 돌리는 프로그램(Claude Code)이 답을 받을 때 한 번 보고, 서버가 한 번 더 본다.

이 스키마에 일부러 넣지 않은 것이 있다. 필드마다 허용되는 값의 목록(enum)이다. 예를 들어 우선순위 필드에 「P0부터 P3 가운데 하나」라는 목록을 넣으면, AI는 목록 밖의 값을 낼 수 없다. 맞는 값을 모르겠어도 목록에서 아무거나 하나를 고른다. 그러면 「AI가 잘 모르겠다」는 신호가 사라진다. 그래서 목록은 넣지 않고, 값이 목록에 있는지는 서버가 따로 본다. 목록 밖의 값이 오면 사람에게 묻는 항목으로 띄운다.

### AI가 「찾아봤다」고 쓴 것을 확인한다

AI는 답에 근거도 같이 적는다. 「이 파일에서 이 단어를 찾아봤는데 0건이었다」, 「이 파일을 읽었다」 같은 식이다. 한편 AI를 돌리는 프로그램은 AI가 실제로 호출한 도구를 한 줄씩 로그로 남긴다. 서버는 AI가 적은 근거를 이 로그와 비교한다. AI가 찾아봤다고 쓴 검색이 로그에 없으면 경고를 띄운다. 「0건」이라고 한 단어가 실제로는 AI에게 준 파일에 들어 있어도 경고를 띄운다. 이 검사가 생긴 사연은 뒤의 「AI 초안을 어떻게 확인했나」에 있다.

작업 화면의 진행 표시도 같은 로그에서 뽑는다. 「Read 중, 도구 7회, 최근 파일」처럼 로그에 남은 것만 보인다. AI에게 지금 몇 단계인지 말해 달라고 시키지 않았다. AI가 스스로 말하는 진행 상황은 믿을 근거가 못 된다.

## 기능 하나씩

Test Case는 보안상 대외비다. 그래서 아래 화면은 모두 도구 시험용 가데이터로 띄웠다. 가짜 Jira, 가짜 시트, 가짜 AI 응답을 쓴 실제 QA Hub 화면이다. 티켓 번호와 제품 이름도 바꿨다.

### TC 작성: 티켓 번호만 넣으면 소스는 서버가 찾는다

TC 작성 화면에서 꼭 채울 칸은 하나다. Jira 티켓 번호를 넣는다. 여러 개를 넣어도 되고, JQL로 검색 조건을 넣어도 된다. 여러 건이면 서버가 티켓 목록을 먼저 보여 준다. 사람이 고른 티켓마다 작업이 하나씩 대기 목록에 올라간다.

<img class="diagram-light" src="/images/qa-hub-tc-input-light.png" alt="TC 작성 화면. 맨 위에 「Jira 티켓 키 또는 JQL」 입력 칸이 있고, 그 아래에 입력 예시가 있다. 다음 칸은 Figma 링크를 넣는 선택 칸이다. 「소스는 서버가 찾습니다」라는 안내 상자에는 소스를 찾는 순서 세 가지가 적혀 있다. 맨 아래에 「TC 초안 만들기」 버튼이 있다." />
<img class="diagram-dark" src="/images/qa-hub-tc-input-dark.png" alt="" aria-hidden="true" />

어느 소스를 읽을지는 보통 사람이 고르지 않는다. 처음에는 저장소와 브랜치를 사람이 골라야 했다. 나는 AI 팀원들에게 「티켓 넘버만 주고 알아서 소스 보게」 해 달라고 했고, 그렇게 바뀌었다. 지금 저장소와 브랜치 칸은 「소스 직접 정하기」 안에 접혀 있고, 서버가 찾은 소스가 틀렸을 때만 연다. 서버는 세 가지 방법으로 소스를 찾는다.

1. Jira 티켓 화면의 개발(Development) 패널에 연결된 코드 변경(MR과 커밋)을 본다.
2. 서버에 클론해 둔 저장소에서, 커밋 메시지나 브랜치 이름에 그 티켓 번호가 든 것을 찾는다.
3. 그래도 없으면 티켓의 구성 요소와 레이블로 저장소를 고르고, 티켓 글에 나온 키워드가 든 파일을 모은다.

셋 다 못 찾으면 티켓 글만 보고 TC를 쓰고, 화면과 기록에 그렇게 적는다.

처음 부딪힌 것은 Jira 티켓 화면의 개발 패널이었다. 같은 요청을 여섯 번 보냈더니 연결된 코드 변경이 세 번만 왔고, 나머지 세 번은 빈 목록이었다. 빈 목록이 와도 「연결된 변경이 없다」는 뜻이 아니었던 것이다. 그래서 서버는 같은 질문을 네 번 하고 결과를 합친다. 클론해 둔 저장소를 뒤지는 두 번째 방법도 늘 같이 쓴다.

작은 함정도 있었다. JQL에서 이슈 유형을 한국어 이름으로 쓰면(`type = 작업`) 결과가 0건이고, 영어 이름으로 쓰면(`type = Task`) 나온다. 그래서 도움말 예시를 영어로 바꿨다. 검색 결과가 0건이면 유형을 영어 이름으로 바꿔 보라고 안내한다.

화면 설계가 있는 프로젝트라면 Figma 링크도 넣는다. 그러면 서버가 Figma에서 그 화면의 구조 정보와 화면 이미지를 받아 작업 폴더에 둔다. 구조 정보는 화면을 이루는 상자와 글자의 목록이다. AI는 티켓, 소스와 함께 그 화면을 읽고 TC를 설계한다. Figma 시안을 읽고 TC를 쓰는 일은 [디자인 시안에서 TC 600개까지](/posts/tc-design-automation/)에서 해 오던 일이다. 화면의 구성과 순서는 구조 정보로 잡는다. 구조 정보에서 글자 칸이 `title` 같은 이름으로만 나오는 곳은 화면 이미지를 보고 채운다. Figma 링크는 만든 TC의 Comment 칸 마지막 줄에도 붙여서, TC를 수행하는 사람이 바로 열어 볼 수 있다.

### 검토: 꼭 정해야 하는 것만 사람에게

AI가 초안을 내면 서버가 행마다 플래그를 붙인다. 플래그는 11가지다. 예를 들면 이런 것이다.

- 「확인이 필요한 줄」: AI 스스로 확신하지 못한다고 적은 줄
- 「모듈·우선순위가 비어 있음」
- 「이번에 읽지 않은 근거 파일」: AI에게 주지 않은 파일을 근거로 댄 경우
- 「읽지 않은 곳에 대한 단정」: 예를 들어 웹 소스를 주지 않았는데 「웹에는 이 기능이 없다」고 쓴 경우

처음에는 플래그가 붙은 행을 사람이 모두 정해야 시트에 쓸 수 있게 했다. 그런데 실제 AI로 처음 두 번 돌려 보니, 두 번 다 시트에 쓸 수 있는 행이 하나도 없었다. 모든 행에 무언가 플래그가 붙었기 때문이다. 모든 행을 사람이 정해야 하니, 하나씩 정할 화면이 필요했다. 그래서 검토 화면을 만들었다.

써 보니 정할 것이 너무 많았다. 나중에 범위를 줄이면서 기준을 하나로 좁혔다. **그대로 쓰면 틀린 사실이 시트에 나가는가.** 이 기준에 걸리는 플래그 여섯 가지만 사람이 정한다. 나머지는 그 행의 Comment 칸에 「확인 필요: …」로 적어 두고 그대로 쓴다. 문장 다듬기는 시트에 쓴 뒤 시트에서 한다.

<img class="diagram-light" src="/images/qa-hub-tc-review-light.png" alt="TC 검토 화면. 위쪽에 다섯 단계 표시가 있고, 지금은 검토 단계다. 오른쪽 위에는 정할 것 3개 중 0개를 정했다는 표시가 있다. 첫 TC는 「정할 것 없음」이다. 둘째 TC에는 플래그 세 개가 붙어 있고, 플래그마다 「이 줄을 빼고 Comment에 남기기」, 「목록에서 값 고르기」, 「이 TC 빼기」 같은 선택지가 있다." />
<img class="diagram-dark" src="/images/qa-hub-tc-review-dark.png" alt="" aria-hidden="true" />

AI가 쓰지 않는 칸도 정했다.

- TC 번호: 서버가 시트 파일의 모든 탭을 읽고 이어지는 번호를 붙인다.
- Jira 요약: Jira에서 그대로 가져온다.
- 결과 칸: 늘 `N/T`(아직 수행 안 함)로 쓴다.
- Comment 칸: AI가 마음대로 쓰지 않는다. 서버가 근거, 확인 필요, Figma 링크 같은 조각을 정해진 순서로 모은다.

TC 문장이 규칙을 지켰는지 보는 문체 검사기도 있다. 내가 공개해 둔 TC 규격 저장소([qa-spec-kit](https://github.com/yungu-k/qa-spec-kit))의 검사기를 고치지 않고 그대로 가져다 쓴다.

### 시트에 쓰기: 끝에 행을 넣고 다시 읽는다

TC는 사람이 고른 탭의 마지막 행 아래에 붙는다. 시트 API가 실제로 어떻게 움직이는지는 하나씩 직접 확인했고, 확인한 결과대로 설계했다.

빈 칸에 값을 덮어쓰지 않고, 새 행을 넣은 뒤 그 행에 쓴다. 서버가 시트를 읽은 뒤 쓰기 전에 다른 사람이 끝에 한 줄을 더했다고 해 보자. 새 행을 넣는 방식이면 그 사람의 줄은 아래로 밀릴 뿐 지워지지 않는다. 행 넣기와 값 쓰기는 요청 하나로 보낸다. 이 요청은 전부 되거나 전부 안 된다.

다 쓰고 나면 칸마다 보낸 값과 다시 읽은 값을 비교한다. 기존 행이 쓰기 전과 같은지, 새 행에 드롭다운과 조건부 서식이 따라왔는지도 본다.

<img class="diagram-light" src="/images/qa-hub-tc-written-light.png" alt="시트에 쓰기를 마친 화면. 「Test Case Template 10행부터 2개 행을 썼습니다. 다시 읽어 칸마다 보낸 값과 비교했고, 모두 같습니다. 기존 행도 쓰기 전과 같습니다」라는 안내와 탭 열기 버튼이 있다. 아래 쓴 기록에는 어느 파일 어느 탭에 썼는지, TC 번호, 누가 언제 썼는지, 어느 규칙 버전으로 만들었는지가 있다." />
<img class="diagram-dark" src="/images/qa-hub-tc-written-dark.png" alt="" aria-hidden="true" />

여러 사람이 같은 시트 파일에 동시에 쓰지 않도록, 쓰는 동안 그 파일을 잠근다. 처음에는 탭 하나만 잠그려 했다. 그런데 TC 번호는 파일 안 모든 탭을 보고 정한다. 또 행을 새로 넣으면 그 아래 행들의 번호가 한 칸씩 밀린다. 그사이 같은 탭에서 Bug 등록이나 Close 확인이 밀리기 전 행 번호로 쓰면 엉뚱한 행에 쓸 수 있다. 그래서 파일 전체를 잠근다. 번호 정하기부터 쓰기, 다시 읽어 비교하기까지가 한 번의 잠금 안에서 일어난다. 사람이 시트에서 직접 고치는 것은 서버가 잠글 수 없다. 그런 경우는 마지막에 다시 읽어 비교하는 단계가 잡는다.

시트를 읽다가 실패하는 경우도 따로 다뤘다. 시트 API는 1분에 읽을 수 있는 횟수가 정해져 있다. 처음 코드는 이 한도에 걸려 못 읽은 칸을 빈 칸으로 여겼다. 못 읽은 탭을 빈 탭으로 보면 TC 번호가 겹칠 수 있다. 지금은 읽기에 실패하면 「시트 사용 한도」인지 「권한 없음」인지 화면에 적고 멈춘다. 탭마다 따로 읽던 것도 한 번에 묶어 읽게 바꿨다. 탭이 많은 가짜 시트로 확인해 보니, 쓰기 전 확인 화면을 한 번 여는 데 드는 읽기가 35번 넘게에서 6번으로 줄었다.

### Bug 등록: 템플릿은 서버가 채우고, AI는 다듬고 원인을 추정한다

버그를 등록할 때는 TC 번호와 문제 현상만 넣으면 된다. 서버가 시트에서 그 TC 행을 찾아 버그 본문 템플릿을 채운다.

- TC의 사전 조건과 수행 절차 → 버그의 재현 절차
- TC의 기대 결과 → 버그의 기대 결과
- 사람이 적은 문제 현상 → 버그의 실제 결과

비어 있는 칸은 지어 넣지 않고 뺀다. 우선순위는 TC의 우선순위(P0~P3)를 Jira의 우선순위(Highest~Low)로 옮긴다. 여기까지는 AI를 부르지 않는다.

처음 계획에서는 버그 등록에 AI를 아예 쓰지 않기로 했다. AI 팀원들이 정한 기본은 「제목·본문은 모델 없이 틀을 채운다.」였다. 써 보니 아쉬웠다. 나는 버그를 올릴 때 늘 그 티켓이 바꾼 소스를 같이 봤기 때문이다. 그래서 이 기본을 뒤집었다. AI가 소스까지 살펴보고 버그 본문을 보완해 주는 기능이 필요했다.

다만 선을 하나 그었다. 버그 본문에는 입력으로 받은 사실만 쓰도록 AI에게 정해 두었다. 입력은 TC 행, 사람이 적은 글, 티켓, 사람이 Bug 화면에서 올린 첨부파일이다. AI가 소스를 보고 추정한 원인은 「참고 — AI 추정(확인 필요)」이라는 별도 칸에만 쓰게 했다. 이 규칙을 지켰는지는 서버가 본다. 서버는 AI가 다듬은 본문에서 티켓 번호, 버전 번호, 두 자리 이상의 숫자, 파일 경로 같은 말을 뽑아 입력에 있던 말인지 확인한다. 없던 말이면 경고를 띄운다. 막지는 않는다. 경고를 보고 고치는 일은 사람이 한다. 실제 AI로 한 번 시험했을 때는 이 경고가 한 건도 뜨지 않았다.

<img class="diagram-light" src="/images/qa-hub-bug-ai-light.png" alt="Bug 등록 미리 보기의 AI 다듬기 상자. AI가 다듬은 제목과 본문을 초안에 넣었다는 안내가 있다. 그 아래 노란 글씨로 「입력(TC·적은 글·티켓·첨부)에 없던 말이 들어갔습니다 — 사실인지 확인하세요」라는 경고와, 입력에 없던 말의 목록이 있다. 아래에는 AI가 읽은 소스, AI 전 글 보기, 「AI 전 글로 되돌리기」 버튼이 있다." />
<img class="diagram-dark" src="/images/qa-hub-bug-ai-dark.png" alt="" aria-hidden="true" />

AI가 다듬는 동안 사람이 초안을 고칠 수도 있다. 그래서 서버는 다듬기를 시작할 때 초안을 기억해 둔다. 다듬기가 끝난 뒤 사람이 화면을 열면, 초안이 그때와 같은지 본다. 같으면 AI 글을 넣는다. 달라졌으면 넣지 않고 「AI 다듬은 글로 바꾸기」 버튼만 보여 준다. 사람이 고친 글을 AI가 덮어쓰지 않게 하려는 것이다.

Jira에 버그를 만드는 순간도 조심했다. 만드는 도중에 연결이 끊기면 버그가 만들어졌는지 알 수 없다. 이때 다시 보내면 같은 버그가 둘 생길 수 있다. 그래서 이 상태를 「모름」으로 두고 자동으로 다시 보내지 않는다. 화면에 이 계정으로 최근 만든 이슈를 보여 주고, 사람이 고르게 한다. Jira가 버그 번호를 돌려주면 바로 기록해 둔다. 그 뒤에 시트 쓰기가 실패해도, 다시 누르면 Jira에는 또 만들지 않고 시트만 고친다.

버그 본문은 Jira의 문서 형식(ADF)으로 보낸다. 옛 위키 문법으로 보내면 TC 글 속의 `[`, `*`, `{` 같은 글자가 링크나 굵은 글씨로 바뀌어 버린다.

버그 등록은 각자의 Jira 계정으로 한다. 처음 접속할 때 Jira 이메일과 API 토큰을 넣으면, 서버가 Jira에 그 사람이 맞는지 물어 확인한다. 토큰은 사람마다 암호화해 서버에 두고, 브라우저에는 로그인 쿠키만 남긴다. 그래서 Jira의 보고자 칸에는 실제로 버튼을 누른 사람이 남는다.

### Close 확인: 「완료」 상태만 닫힌 것으로 본다

Close 확인은 TC 탭에서 Fail인 행을 모아, 그 행에 연결된 버그가 Jira에서 모두 닫혔는지 본다. 모두 고쳐져 닫혔으면 Pass 후보로 보여 주고, 사람이 고른 행만 Pass로 바꾼다. [티켓은 완료인데 TC는 Fail](/posts/regression-and-status-sync/)에서 정한 「버그가 완료되면 Pass」 규칙을 QA Hub로 옮긴 것이다.

이 메뉴는 TC를 다시 수행하지 않는다. Jira에 적힌 버그 기록만 보고, Pass로 바꿀 만한 행을 골라 보여 준다. 다시 수행할지, 어느 행을 Pass로 바꿀지는 사람이 정한다. AI도 부르지 않고 Jira에 쓰지도 않는다. 버그를 닫는 일은 사람이 Jira에서 한다.

버그가 닫혔는지는 상태가 「완료」인지만 보고 판단한다. Jira는 「완료」와 「FIXED」를 같은 Done 상태 카테고리에 넣어 두어서, Jira 화면에서는 두 상태가 같은 색으로 보인다. 하지만 우리 팀 보드에서 FIXED는 개발이 고쳤을 뿐 아직 QA가 확인하지 않은 「진행 중」 상태다. Jira의 상태 카테고리대로 판단하면, QA가 확인하지 않은 버그의 TC까지 Pass 후보로 뜬다. 그래서 Jira의 상태 카테고리 대신 우리 팀이 일하는 방식을 따랐다. 「중복된 이슈」나 「재현 불가」처럼 고치지 않고 닫힌 버그는 Pass 후보에서 빼고 따로 보여 준다.

<img class="diagram-light" src="/images/qa-hub-close-light.png" alt="Close 확인 결과 화면. Pass 후보 한 행에는 체크 상자가 켜져 있고, 연결된 버그의 상태와 해결 방식이 보인다. 「고른 행을 Pass로 바꾸기」 버튼 옆에, 누르는 순간 탭과 Jira를 다시 읽어 그사이 바뀐 행은 쓰지 않는다는 안내가 있다. 아래에는 아직 닫히지 않은 버그가 있는 행이 따로 묶여 있고, FIXED 상태인 버그도 「남음」으로 여기에 들어간다. 고치지 않고 닫힌 행, 연결된 버그가 없는 행, 읽지 못한 티켓이 있는 행도 따로 묶여 있다." />
<img class="diagram-dark" src="/images/qa-hub-close-dark.png" alt="" aria-hidden="true" />

Jira에는 버그 번호를 100개씩 묶어 JQL 한 번으로 묻는다. 그런데 없는 번호가 하나라도 섞이면 JQL 전체가 거절된다. 그래서 거절되면 그 묶음만 번호 하나씩 다시 묻는다. 그러면 어느 번호가 문제인지 화면에 「못 읽은 티켓」으로 나온다. 못 읽은 번호가 걸린 행은 Pass 후보에서 뺀다. 읽지 못한 버그를 닫힌 것으로 치지 않기 위해서다.

### QA Report: 숫자는 AI에게 맡기지 않는다

QA Report는 시트의 TC 탭과 결과 탭, 그리고 Jira를 읽어 Sign-off Report를 PDF와 HTML로 만든다. 통과율, 결함 수, 우선순위별 분포 같은 숫자와 표는 전부 생성 코드가 계산한다. AI가 맡는 일은 하나뿐이다. 생성 코드가 쓴 설명 문장을 읽기 좋게 다듬는 일이다.

AI에게는 다듬을 문장만 맡긴다. 표와 시트 글은 맡기지 않는다. 문장 안에도 숫자가 들어 있는데, AI가 그 숫자를 바꾸면 안 된다. 그래서 서버는 다듬기 전 문장과 다듬은 뒤 문장에서 숫자와 티켓 번호를 하나하나 꺼내 맞춰 본다. 하나라도 다르면 Report를 내지 않고 멈춘다.

<img class="diagram-light" src="/images/qa-hub-report-stop-light.png" alt="QA Report 작업이 멈춘 화면. 제목 옆에 「실패」 표시가 있고, 글자 검사(HTML) 단계가 실패해 Report를 만들지 못했다는 안내가 있다. 아래 발행 전 자동 검사 목록에서 문장 다듬기 검사는 통과, 글자 검사(HTML)는 실패로 표시돼 있다." />
<img class="diagram-dark" src="/images/qa-hub-report-stop-dark.png" alt="" aria-hidden="true" />

Report 생성 코드에는 Report를 멈추게 하는 조건이 곳곳에 있다. 예를 들면 시트의 요약 칸과 생성 코드가 계산한 수가 다를 때, 결과 칸에 모르는 값이 있을 때, 결함 수가 Jira와 다를 때 멈춘다. Report에 「확인 필요」라는 글자가 남아 있을 때도 멈추고, 「시트에서 정리한 뒤 다시 요청하세요」라고 안내한다.

Report를 내기 전에는 다섯 단계를 거친다.

1. 다듬기 전과 뒤의 문장에서 숫자와 인용이 같은지 본다
2. HTML에 PDF에서 깨지는 글자가 없는지 본다
3. PDF를 만든다
4. PDF에 글자가 실제로 들어갔는지 본다
5. 메일에 붙여 쓸 요약 HTML에 Report에 없는 티켓이나 숫자가 없는지 본다

하나라도 실패하면 Report를 내지 않는다. 검사 프로그램이 서버에 없을 때도 멈춘다. 검사 없이 나간 Report보다 멈춘 화면이 낫다.

### 로그 분석: 근거 로그는 서버가 다시 확인한다

로그 분석은 처음 계획에 없던 메뉴다. TC 작성, Bug 등록, Close 확인, QA Report를 만든 뒤에 추가한 기능이다. 운영 알람과 로그를 AI로 분류하던 일(맨 앞 표의 다섯째 줄)을 QA Hub로 옮긴 것이다. 로그 파일을 올리거나, 로그가 첨부된 Jira 티켓 번호를 넣고 증상을 적으면 된다.

서버는 받은 zip 파일을 풀고, 한글이 깨지지 않게 글자 인코딩을 맞추고, 비밀 값을 마스킹한다. 파일마다 줄 수, 기록된 시각의 범위, 오류 줄 수를 적은 목차 파일도 만든다. AI가 큰 로그를 처음부터 다 읽지 않고, 필요한 곳을 찾아 들어가게 하려는 것이다. 비교할 소스는 저장소에서 정한 브랜치나 커밋의 코드를 통째로 꺼내 둔다. AI는 원인 후보마다 근거가 되는 로그와 관련 소스 위치를 낸다. 근거 로그는 파일 이름, 줄 번호, 그 줄의 내용으로 적는다.

서버는 AI가 댄 근거 로그를 자기가 정리해 둔 로그 파일에서 다시 찾아 세 가지를 본다. 파일이 받은 자료 안에 있는지, 줄 번호가 파일 길이 안인지, AI가 옮겨 적은 내용이 그 줄 앞뒤 3줄 안에 정말 있는지다. 서버는 AI의 결과로 Jira에 올릴 코멘트 초안을 만드는데, 확인되지 않은 근거는 이 초안에서 뺀다. 근거가 하나도 남지 않은 후보는 후보째 뺀다. 코멘트 첫 줄에는 서버가 정해 둔 글이 들어간다. 「AI가 로그와 소스를 읽고 찾은 원인 후보입니다. 확정된 원인이 아닙니다.」

<img class="diagram-light" src="/images/qa-hub-log-light.png" alt="로그 분석 결과 화면. 맨 위 노란 상자에 「AI가 찾은 원인 후보입니다. 확정된 원인이 아닙니다」와 테스터가 할 일이 적혀 있다. 요약 카드에는 비교한 소스가 있고, 현장 장비에 깔린 버전과 다르면 AI가 맞지 않는 코드를 근거로 댔을 수 있다는 경고가 있다. 아래 원인 후보 카드에는 근거 로그 파일과 줄 번호, 「로그에 있음」 표시, 옮겨 적은 로그 줄, 관련 소스 경로가 있다." />
<img class="diagram-dark" src="/images/qa-hub-log-dark.png" alt="" aria-hidden="true" />

근거 로그 옆에는 「로그에 있음」 표시가 붙는다. AI가 옮겨 적은 내용이 로그의 그 위치에 정말 있다는 뜻이다. 원인이 확인됐다는 뜻은 아니다.

예전에 사람이 직접 원인을 찾았던 장애가 하나 있다. 그 장애의 로그를 실제 AI로 돌려 보니, 그때 사람이 찾은 원인과 같은 후보를 냈다. 코멘트는 사람이 읽고 고친 뒤 [Jira에 코멘트 등록]을 눌러야 등록된다. 등록은 누른 사람의 계정으로 한다.

### 자동화 결과: 실제로 시험한 버전을 본다

자동화 결과 메뉴는 Regression Test 결과를 모아 보는 곳이다.

키오스크 웹 화면의 Regression Test를 돌리는 서버(QA 러너)에는 평소 기준이 되는 버전이 깔려 있다. 개발 빌드가 새로 나오면 QA 러너가 그 빌드로 바꿔 깔고 시험한 뒤, 끝나면 평소 버전으로 되돌린다. QA 러너가 새 빌드를 찾아 시험하는 방식은 전부터 있었다. 이번에는 Jenkins가 빌드가 끝나자마자 QA 러너를 깨우고, 결과 요약을 QA Hub로 보내게 했다. QA Hub는 그것을 목록에 쌓고 팀 메신저 방에 한 통 알린다.

## AI 초안을 어떻게 확인했나

TC 작성은 AI를 가장 많이 쓰는 기능이라 가장 오래 확인했다.

### 정할 것 0건이 좋은 소식이 아니었다

같은 티켓으로 규칙을 고쳐 가며 여러 번 돌렸다. 사람이 정할 플래그를 여섯 가지로 좁히기 전의 일이다. AI 초안 하나에 사람이 정해야 할 것이 몇 건 나오는지, 규칙을 고칠 때마다 무엇이 바뀌는지 봤다.

처음에는 정할 것이 25건이었다. 같은 질문이 여러 행에 되풀이됐고, AI에게 준 코드는 최신이 아니었으며 필요한 파일도 빠져 있었다. 같은 질문은 하나로 묶어 묻도록 규칙을 고치고 최신 코드를 주자, 정할 것이 3건으로 줄었다. 남은 3건 가운데 하나는 AI가 규칙 문장을 잘못 읽어서 생긴 질문이었다. 그 문장을 고친 다음 실행에서는 정할 것이 0건이 나왔다. 나머지 두 건까지 사라진 것이다.

0건을 보고 반가웠지만, 열어 보니 좋은 소식이 아니었다. AI는 티켓 설명과 실제 코드가 다른 곳을 세 군데 찾아 놓고, 그것을 시트로 나가지 않는 칸에만 적어 두었다. AI가 스스로 세운 가정을 적는 칸이다. 이유는 「화면에서 확인할 결과에는 영향이 없어서」였다. 규칙에는 그런 예외가 없었다. AI가 스스로 예외를 만든 것이다. 그대로 썼다면 시트에는 그 차이를 알리는 줄이 하나도 없었을 것이다.

그래서 화면에서 확인할 결과가 같아도 티켓과 코드가 다르면 올리라고 규칙에 적었다. 이번에는 정할 것이 20건으로 늘었다. 숨었던 세 군데에 하나가 더 드러나, 실제 차이는 4개였다. 대신 같은 차이가 행마다 따로 올라와서, 이 4개와 차이가 아닌 것 하나가 9건이 됐다.

나머지 대부분은 문장 형태 하나에서 나왔다. 사전 조건 끝에 상태를 괄호로 덧붙인 형태 때문에 문체로 정할 것이 10건 생겼다. 그래서 같은 차이는 하나로 묶고 괄호를 덧붙이지 않게 고치는 안을 세웠다. AI를 다시 돌리지는 않고 이 안을 같은 결과에 적용해 계산해 보니, 정할 것은 6건이 됐다.

이 과정에서 TC 규칙을 쓰는 기준이 셋 생겼다.

1. 「영향이 없으면 빼도 된다」 같은 판단을 AI에게 맡겼더니 AI는 차이를 시트로 나가지 않는 칸에만 적었다. 올려야 할 것은 예외 없이 규칙에 적는다.
2. 같은 사실은 한 번만 묻게 묶는다.
3. 정할 것이 줄면 무엇이 빠졌는지부터 확인한다. 숨은 차이를 찾는 검사도 이때 따로 만들었다.

### 「지어낸 것 없음」이 뒤집혔다

어느 티켓의 결과를 보면서 처음에는 「지어낸 것 없음」으로 봤다. 그때 본 것은 화면 문구와 근거 파일 경로뿐이었다. 그런데 다른 티켓의 결과를 보다가 이상한 줄을 찾았다. AI는 근거 칸에 telegram이라는 단어를 찾아봤고 0건이었다고 적었다. 하지만 AI의 도구 호출 로그에는 telegram을 찾은 적이 한 번도 없었다. 게다가 AI에게 준 파일 4개에 그 단어가 13줄이나 있었다. AI가 하지 않은 검색을 했다고 쓴 것이다.

앞에서 적은 「찾아봤다고 쓴 것을 확인하는」 검사는 이 일 뒤에 생겼다. 그 검사로 처음 티켓의 결과를 다시 보니, 거기에도 하지 않은 검색이 두 건 있었다.

### 처음 보는 티켓 다섯 건

규칙을 더 고치지 않은 채, AI가 처음 보는 티켓 다섯 건으로 다시 확인했다. 이 티켓들에는 사람이 전에 작성한 TC가 있어서 비교할 수 있었다.

AI는 다섯 건에 TC 67행을 냈고, 그중 64행이 시트에 들어갔다. 없는 화면 문구나 없는 파일을 지어낸 곳은 없었다. 시트에 틀린 사실이 나간 곳도 없었다.

다만 한 티켓에서는 앞의 telegram과 비슷한 일이 다시 나왔다. AI가 근거 칸에 검색으로 찾았다고 적은 것 네 건이 실제 도구 호출 로그에 없었다. 그중 셋은 파일을 직접 읽어 본 내용을 검색한 것처럼 적은 것이라, 적은 내용 자체는 맞았다. 나머지 하나는 하지 않은 검색에 「정의가 입력에 없다」는 틀린 결론까지 붙어 있었다. 그 함수의 정의는 AI에게 준 파일에 있었다. 네 건 모두 시트로 나가지 않는 칸이었다.

사람이 정해야 할 것은 다섯 건을 합쳐 38건이었다. 그중 절반은 AI에게 준 소스가 모자라서 생긴 질문이었다.

사람이 작성한 TC와는 얼마나 겹쳤을까. 사람이 작성한 TC에서 「이렇게 하면 이렇게 보인다」는 확인을 한 쌍씩 뽑으니 53개였다. 그 가운데 AI TC에 그대로 들어 있는 것은 32%였고, 일부만 들어 있는 것까지 합치면 60%였다.

이 비율은 사람이 작성한 TC를 기준으로 본 것이라, 반대쪽도 같이 봐야 한다. AI TC에는 사람이 확인하지 않은 것이 18개 더 있었다. 반대로 사람이 확인한 53개 중 21개는 AI TC에 없었다. 그 절반은 AI에게 준 자료가 모자라서였다. 예를 들어 한 티켓은 키오스크 화면 파일이 입력에 하나도 없었다.

이 비교는 AI QA 팀원(세션) 둘이 서로의 결과를 보지 않고 따로 했다. 사람이 다시 확인한 것은 아니다. 두 AI 팀원의 수는 평균 내지 않고 나란히 적기로 처음부터 정해 두었다. 이번 다섯 건에서 다른 AI 팀원이 낸 비율은 30%로, 32%와 거의 같았다.

그 전에 측정한 다른 다섯 건에서는 두 AI 팀원(세션)의 의견이 36%와 20%로 크게 갈렸다. 갈린 이유로 가장 많았던 것은 확인 하나의 단위를 어떻게 잡느냐였다. 한쪽은 화면에 보여야 할 결과 하나를 하나로 쳤고, 다른 쪽은 누르기나 입력 같은 조작 하나를 하나로 쳤다.

두 AI 팀원에게 준 판정 기준 문서에는 「확인 하나」를 나누는 규칙이 있었다. 하지만 그 규칙에는 두 가지로 읽히는 부분이 남아 있었고, 두 AI 팀원은 그 부분을 서로 다르게 읽었다. 지시가 충분히 자세하지 않았던 것이다. 평균을 냈다면 이 차이가 숫자 하나에 묻혀, 기준 문서에 빈 곳이 있다는 것도 몰랐을 것이다. 이 부분은 다음 기준 문서에 더 분명히 적을 것으로 남겼다. AI 둘에게 같은 일을 시킬 때는 무엇을 하나로 볼지 분명히 정해 줘야 한다.

겹치는 정도와 별개로, 실무에서는 AI가 쓴 TC가 이미 사람이 쓰던 TC를 대신하고 있다. 최근 Release에서는 TC를 사람이 따로 쓰지 않았다. 내 PC의 자동화가 규칙대로 쓴 TC를 내가 조금 리뷰하고 그대로 수행했다. 지금도 그렇게 일한다.

물론 AI가 쓴 TC가 모든 부분을 커버하는 것은 아니다. 앞서 시험한 다른 티켓에서 이런 일이 있었다. 장비 외관 문이 위아래로 둘 있다. 사람이 작성한 TC는 두 문을 나눠 따로 확인했고, 위쪽 문에서 실제 결함을 찾았다. 결함을 고친 뒤에는 위쪽 문을 열 번 반복해 다시 확인했다. AI TC에는 문 구분이 없었다. AI가 남긴 메모를 보면 이유가 보인다. AI는 코드에서 두 센서 중 하나라도 감지되면 열림으로 처리한다는 것을 읽었고, 위쪽 문 결함은 고쳐진 코드가 기준이라고 적었다. 메모대로라면 AI는 두 문의 결과가 같다고 보고 한 경우로 다뤘다. 그런데 코드는 어느 문을 여느냐에 따라 실행 경로가 달랐고, 티켓 댓글에도 위쪽 문이 이름으로 나와 있었다. AI에게 준 자료만으로도 나눌 수 있었던 것이다. 반대로 같은 티켓에서 AI는 티켓에 적힌 검증 항목 가운데 사람이 작성한 TC에 없던 세 가지를 채웠다.

그래서 동료 리뷰(Peer Review)를 하듯 AI도 한 명의 동료로 보고 리뷰하는 과정이 반드시 필요하다. 이번 확인에서 리뷰할 때 볼 지점이 드러났다. 결과가 같다고 한 경우로 묶은 곳이 실제로는 대상이 둘 이상이 아닌지 본다. 결함이 났던 곳을 AI가 고쳐진 코드만 보고 넘기지 않았는지 본다. AI에게 준 자료에 빠진 화면이나 파일이 없는지도 본다. QA Hub도 이 흐름에 맞췄다. 꼭 정할 것만 사람이 정한 뒤 시트에 쓰고, 리뷰와 수정은 시트에서 한다.

## 만드는 방식: AI 팀원 여럿이 저장소 하나로

QA Hub는 AI 팀원 여럿이 저장소 하나를 같이 쓰며 만들었다. 총괄을 맡은 AI 팀원이 범위와 순서를 정했다. QA를 맡은 AI 팀원 둘이 요구사항과 테스트를, 개발 AI 팀원이 서버를, 디자인 AI 팀원이 화면을 맡았다. 기획 AI 팀원은 화면 흐름을 검토했다. 이 절에서 「팀원」은 모두 AI 팀원이다. 각자 자기 폴더만 고치고, 커밋할 때는 넣을 파일을 하나씩 지정한다. 다른 팀원이 고치다 만 파일이 자기 커밋에 섞여 들어가지 않게 하려는 것이다.

### QA가 테스트를 먼저 짰다

QA 팀원은 개발 팀원이 기능을 만들기 전에 자동 테스트부터 짰다. 아직 없는 기능을 부르는 테스트는 「실패」 가운데서도 「아직 없음」으로 따로 구분한다. 그래서 기능을 만들기 전에도 테스트를 돌릴 수 있다.

테스트에 쓰는 가짜 시트에도 규칙이 하나 있다. 진짜 시트 API로 직접 확인한 동작만 흉내 낸다. 확인하지 않은 요청이 오면 오류를 내며 멈춘다. 행을 넣는 위치 같은 동작이 모두 이 가짜 시트에 들어 있다.

테스트가 정말 실패를 잡을 수 있는지도 확인했다. 11월 24일 운영 판의 QA 테스트 150개를 예전 시점의 코드에 돌리면 이렇게 나온다.

| 코드 시점 | 실패 | 통과 | 아직 없음 |
| --- | --- | --- | --- |
| 첫 구현 | 35 | 40 | 75 |
| 네 기능 중 셋이 들어온 뒤 | 2 | 120 | 28 |
| 11월 24일 운영 판 | 0 | 150 | 0 |

코드에 결함을 일부러 넣어 보는 변이 테스트도 같이 돈다. 테스트가 도는 동안에만 앱 함수 하나를 망가진 것으로 바꿔 놓고, 그 결함을 잡기로 한 테스트가 모두 실패하는지 본다. 「기존 행을 덮어씀」, 「못 읽은 탭을 빈 탭으로 읽음」, 「통과율 계산을 바꿈」 같은 결함 35개를 넣었고, 35개 모두 잡혔다. 변이 테스트를 처음 해 본 이야기는 [버튼 하나를 일부러 망가뜨렸다](/posts/kiosk-mutation-testing/)에 있다.

실제 시험 시트에도 다루기 까다로운 값 12가지를 값마다 12칸씩 써 보고 다시 읽었다. `=1+1`, 작은따옴표로 시작하는 글, 칸 안의 줄바꿈, 이모지 같은 것이다. 모두 144칸이었고, 모두 보낸 그대로 돌아왔다.

### 디자인 없이 만든 화면

범위를 줄이던 때라 디자인 팀원은 잠시 쉬게 해 두었다. 개발 팀원은 새 기능 화면을 임시 스타일로 빠르게 만들었다. 다크 모드로 새 화면들을 열어 보니 이런 문제가 있었다.

- 어두운 바탕에 흰 선택 상자가 두 개 떠 있었다.
- 입력 폼과 경고 띠의 폭이 서로 달랐다.
- 칸 안의 예시 글이 이미 들어간 값처럼 보였다.
- 연한 파랑 버튼이 눌리지 않는 버튼처럼 보였다.
- 「모델을 부르지 않는다」 같은 개발자 말이 화면에 그대로 나왔다.

캡처를 붙여 「디자인 세션을 안 켜 놨더니 아주 난리가 났구나」라고 보냈다.

이 일로 하네스 엔지니어링이 왜 중요한지 다시 확인했다. 하네스(harness)는 AI가 일하는 틀이다. AI 팀원마다 맡을 역할, 고칠 수 있는 폴더, 읽을 규칙 문서를 이 틀로 정해 둔다. 각자 지정된 영역 밖의 일은 함부로 건드리지 않게 하려는 것이다. 그때 디자인 팀원의 영역은 시안이었고, 앱 화면 파일은 개발 팀원의 영역이었다. 디자인 팀원이 쉬는 동안에는 새 화면을 디자인 쪽에서 봐 줄 팀원이 없었다. 영역을 나눠 두면 맡은 팀원이 없는 영역은 비어 있게 된다. 그래서 역할마다 그 일을 맡은 AI 팀원이 실제로 켜져 있어야 한다.

원인을 보니 화면 스타일이 두 종류였다. 화면 열두 개 가운데 열 개가 임시 스타일을 쓰고 있었다. 디자인 팀원을 다시 불러, 이번에는 시안을 따로 그리지 말고 앱 화면 파일을 직접 고치게 했다. 디자인 팀원은 화면 스타일을 하나로 합치면서, 화면을 검사하는 도구도 같이 만들었다. 가짜 Jira, 가짜 시트, 가짜 AI로 화면을 상태별로 하나씩 띄우고, 위의 다섯 가지 문제가 있는지 지점마다 확인한다. 예전 화면은 도구가 검사한 지점의 절반 넘는 곳에서 걸렸고, 새 화면은 한 곳도 걸리지 않았다.

같은 도구로 한글 단어가 줄 끝에서 중간에 잘리는 곳도 확인했다. 그사이 화면이 14개로 늘었는데, 화면 14개를 세 가지 폭으로 띄워 보니 단어가 중간에 잘린 곳이 365곳이었다. 줄바꿈 규칙(CSS `word-break`)을 `keep-all`로 바꾼 뒤에는 화면에 실제로 들어가는 글에서 한 곳도 잘리지 않았다. 이 글의 화면 캡처도 이 도구로 띄운 화면이다.

사용 가이드는 처음 읽는 사람 역할의 AI에게 읽혀 가며 다듬었다. 이 AI에게 가이드를 문장마다 자기 말로 풀어 보게 했다. 처음 쓰는 사람에게 낯선 동사나, 한 단어를 두 뜻으로 쓴 곳에서 막혔다. 가이드가 화면 문구를 그대로 인용하고 있어서, 화면 문구부터 고쳐야 가이드가 고쳐졌다. 「거르기」라는 화면 이름은 이때 「검토」가 됐다. 「거르기」가 필터처럼 읽힌다는 이유였다.

## 걷어낸 것들

QA Hub를 만든 시간의 꽤 많은 부분이 걷어내는 데 들었다.

### 범위를 네 기능으로 줄였다

처음에는 넓게 시작했다. TC 작성과 Report 메일 발송이 기본이었고, AI에게 일을 시키는 규칙 md까지 웹에서 보고 바로 고치는 화면도 계획했다. 실제로는 규칙을 보는 화면까지만 만들었다. 이런 것도 있었다.

- 실행할 때마다 시트에 새 탭을 복사해 쓰는 방식
- 사용자가 이름을 직접 적는 방식
- 한 사람이 대기 목록에 올릴 수 있는 작업 수를 묶어 두는 장치

AI 초안을 측정하려고 만든 도구와 자료도 금방 커졌다.

그 뒤 범위를 줄였다. 넓게 만들던 것을 우리가 실제로 일하는 순서에 맞추기로 했다. 그 순서는 이렇다.

1. 기획서 및 Jira 티켓을 넣으면 시트에 TC를 만든다.
2. 버그가 생기면 TC 번호와 문제 현상으로 버그를 등록하고, TC에 Fail과 버그 링크를 남긴다.
3. Close된 티켓이 있으면 TC를 Pass로 바꾼다.
4. 테스트 결과 시트를 바탕으로 QA Report PDF와 HTML을 뽑는다.

네 기능 가운데 Bug 등록, Close 확인, QA Report는 이때 QA Hub 메뉴로 새로 옮겼고, TC 작성은 탭 끝에 행을 붙이는 방식으로 바꿨다. AI 초안을 측정하던 도구와 자료는 지우지 않고, 더 고치지도 않기로 했다.

메일은 이렇게 빠졌다. 원래는 QA Report 메일을 서식까지 갖춰 만들어 주는 기능이었다. 그런데 정작 나는 Sign-off 메일을 직접 쓴다. 예전에 서식을 입힌 메일용 HTML을 받고 1분 뒤에 「그냥 PDF로 공유해야겠다~」라고 한 적도 있었다. 그래서 메일을 보내는 기능은 걷어냈다. 지금은 Report를 만들면 PDF, HTML과 함께 메일에 붙여 쓸 요약 HTML이 나오고, 메일은 그것을 보고 내가 쓴다.

TC를 도구 안에서 칸 하나씩 고치는 편집 화면도 만들지 않았다. 기획 AI 팀원은 이런 화면이 만들기도 검사하기도 비싸다고 봤다. 여러 사람이 동시에 고칠 때, 사람이 입력하는 도중의 포커스 처리, 긴 칸을 어떻게 보여 줄지 같은 문제가 따라온다. 그리고 「구글 시트는 이미 이걸 한다.」 그래서 도구는 꼭 정할 것만 묻고, 다듬기는 시트에서 한다. 대가는 일이 도구 안에서 끝나지 않는다는 것이다. 시트를 한 번 더 열어야 한다.

### 범위를 줄이면서 팀에 공개했다

범위를 줄이면서, 원래 나중으로 미뤄 둔 공용 운영도 앞당겼다. 처음 계획은 내 PC에서 먼저 써 보고 나중에 사내 서버로 옮기는 것이었다. 그런데 이 도구를 만드는 이유가 팀이 같이 쓰는 것이니 미룰 이유가 없었다. 공용으로 가기로 정하자 사람별 Jira 로그인, 파일 단위 쓰기 잠금, 사내 서버 배포 절차가 차례로 들어왔다.

사내 서버에 처음 설치할 때 작은 사고가 있었다. 설치할 라이브러리 목록 파일(`requirements.txt`)에 한글 주석이 있었는데, 서버의 오래된 설치 도구가 이 한글을 읽다가 멈췄다. 설치 명령을 quiet 옵션으로 돌려서 실패가 눈에 띄지 않았고, 앱을 띄우는 단계에서야 드러났다. 지금은 그 파일에 영문자만 쓰도록 테스트가 막는다.

### 버그를 닫을 때가 아니라 빌드마다 Regression Test를 본다

버그가 고쳐져 이슈를 닫을 때 기본 Regression Test가 자동으로 돌고, 그 결과가 QA Hub에 공유되게 해 달라고 요청한 적이 있다. 설계는 버그의 Fix Version으로 수정이 들어간 빌드를 찾고, 그 빌드에서 돈 결과만 붙이는 방식이었다. 정할 것 다섯 가지를 내가 정했고, 개발 AI 팀원이 구현까지 마쳤다.

그러다 Jenkins에서 CI/CD 파이프라인을 구축하면서 생각이 바뀌었다. 앞의 「자동화 결과」에 적은 대로, 이제 키오스크 웹은 개발 빌드가 성공하면 Jenkins가 바로 QA 러너를 깨워 그 빌드로 Regression Test를 돌리고, 결과가 QA Hub로 온다. 수정은 빌드에 실려 오니, 빌드마다 돈 결과를 보면 된다. 버그를 닫는 순간에 따로 돌릴 이유가 없었다. 구현한 코드는 main 브랜치에 넣지 않고 따로 보관했다. 그 대신 빌드마다 돈 결과를 QA Hub 자동화 결과 메뉴가 받는다.

## 그래서 지금 QA Hub는

| 메뉴 | AI가 하는 일 | 서버가 검사하는 것 |
| --- | --- | --- |
| TC 작성 | 티켓, 소스, Figma 화면을 읽고 TC 초안 쓰기 | 응답 스키마, 행마다 붙는 플래그 11가지(그중 6가지는 사람이 꼭 정함), 도구 호출 로그와 비교, 쓴 뒤 다시 읽기 |
| Bug 등록 | 본문 다듬기, 별도 칸에 원인 추정 | 입력에 없던 말, 「모름」 상태, 시트 다시 읽기 |
| Close 확인 | 없음 | 「완료」 상태, 고치지 않고 닫힌 버그 빼기, 못 읽은 번호, 누르는 순간 다시 읽기 |
| QA Report | 설명 문장 다듬기만 | 숫자와 번호 맞춰 보기, Report를 멈추게 하는 조건, 발행 전 다섯 단계 |
| 로그 분석 | 원인 후보와 근거 로그 | 근거 로그를 그 줄 앞뒤 3줄에서 다시 찾기, 확인 안 된 근거 빼기 |
| 자동화 결과 | 없음 | 받은 결과 요약의 형식 |

이 표에서 「서버가 검사하는 것」 칸이 내 PC 시절과 지금의 차이다. 내 PC에서 쓸 때는 그 칸을 내가 머릿속으로 채웠다.

## 사내 QA를 모두 같은 도구로

이제 사내 QA는 모두 같은 도구인 QA Hub를 거쳐서 할 수 있다. 내가 이 도구에서 가장 중요하게 보는 것도 이것이다. TC 초안 만들기, 버그 등록, Pass로 바꿀 행 고르기, QA Report, 로그 분석, 자동화 결과 확인이 모두 서버 한 대의 화면에서 시작한다. TC 문장을 시트에서 다듬고 Sign-off 메일을 쓰는 일은 지금도 도구 밖에서 한다. 그래도 그 재료는 누가 하든 같은 화면에서 나온다. QA Hub 전에는 이 일들 대부분이 내 PC에서만 돌았다. 동료가 같은 일을 하려면 내 설정을 통째로 옮기거나 손으로 해야 했다.

한 도구로 모아서 투입한 리소스가 얼마나 줄었는지는 따로 측정하지 않았다. QA Hub를 만든 목적이 리소스를 줄이는 데 있지 않아서다. 일마다 걸리던 시간은 4월부터 자동화를 하나씩 만들면서 이미 줄여 왔다. QA Hub는 그 자동화들을 팀 모두가 같은 AI-Native Workflow로 쓰게 하는 Hub 역할을 하려고 만들었다. 모으고 나서 바뀐 것은 이렇다.

- TC를 만들 때는 누구의 요청이든 같은 버전의 규칙 md를 읽고, 어느 버전을 썼는지 작업 기록에 남는다. 규칙 md 한 줄을 고치면 다음 요청부터 팀 모두가 새로 만드는 TC에 반영된다.
- AI 초안은 버튼을 누른 사람이 누구든 같은 검사를 거친다.
- QA Hub로 시트에 쓸 때는 파일 하나를 잠근 채 번호를 정하고 행을 넣은 뒤 다시 읽어 비교한다. 두 사람이 QA Hub로 같은 시트에 동시에 써도 서로의 행을 덮지 않는다.
- Report의 숫자와 표는 만드는 사람과 상관없이 같은 코드가 계산한다.
- Jira에는 각자 자기 계정으로 쓴다. 대기 목록이 모두에게 보여서, 누가 어떤 티켓을 넣었는지 볼 수 있다.

[3년 전과 지금, 내 QA 업무를 나란히 놓았다](/posts/qa-now-ai-native/)의 끝에 「다음 단계는 공통 문서다」라고 적었다. 기획·개발·QA가 쓰는 AI가 같은 문서를 바라봐야 한다는 이야기였다. QA Hub는 그중 QA 쪽이고, 여기서 그 문서는 앞에서 말한 TC 규칙 md다.
