# [저자 확인] 답변 시트 — P3 수치 주입용

> `답:` 뒤에 기입. **실측 없으면 "없음"이라고 적어도 됨** — 그 경우 집행 세션이 "추정임을 명시" 또는 "사례 고정"으로 대체함 (감사 지시에 대체 문형 있음).
> 대략치도 OK — 단 대략치면 "약 N" 으로 표기. **절대 창작 금지 원칙이므로 모르는 값은 비워두지 말고 "없음/모름" 명기.**

## ✅ 최종 판정 (2차 검토 완료 — 이 시트 확정, 집행 세션은 아래 기준으로 진행)

- **모순 1 해소**: 버그 다발 시기 = **신규 프로젝트 테스트 초반부**. → bug-report 도입 훅을 "회귀 한 바퀴 50건" 대신 "신규 프로젝트 테스트 초반, 버그가 수십 건씩 쏟아지는 시기" 기준으로 재작성. 건당 5분 × 수십 건 = 반나절 논리는 유지 가능.
- **모순 2 해소**: 342 = **여러 프로젝트 리그레션 총합**, 120 = 해당 글 프로젝트의 회귀 스위트. 본문의 "120개"는 유지하되 "전수 TC 대비 비율" 표현은 분모 미확보로 **포기** — 대신 21번 답(회귀 1바퀴 2일)으로 "120건 = 2일 분량" 소요 접지.
- **14·18·22·23번 — 2차에서도 미기입 → 미확보 확정.** 집행 세션은 해당 항목 수치 주입 생략, 본문 해당 문장은 사실 범위 한정으로만 손질 (창작 금지).
- **33번 환산 확정**: 사람 하루 150~200건 수행 → **1,160건 ≈ 6~8일치 회귀**.
- **34번**: 6번 재사용 승인 — getting-started "압도적" → "수동 5일 → 자동 2~3시간(검토 별도)" 인용.
- **4번류 "실측 비교 안 함"**: 본문에 추정·체감 기준임을 명시하고 사용.

## ⚠ 검토 노트 (Technical Writer 세션, 1차 답변 검토 후)

- **모순 1 — bug-report 도입 훅과 충돌**: 본문은 "회귀 한 바퀴에 50건이면 반나절"인데 답변 2번은 "회귀에서 결함 보통 1건(혹은 0)". → 집행 세션 지시: 도입 훅을 회귀가 아니라 **신규 기능 테스트 시기** 기준으로 재작성하거나, "많이 나올 때" 조건을 달 것. 50건이라는 가정 수치는 실태와 어긋나므로 그대로 두면 안 됨. [저자 확인: 버그가 하루 수십 건씩 나오는 시기가 실제로 언제인지 — 신규 릴리스 직후? 답: 버그가 수십건 나오는 시기는 신규 프로젝트의 테스트 초반부임.]
- **모순 2 — regression 본문 "120개"와 342의 관계**: 본문은 "회귀 스위트 120개 규모 유지", 답변 20번은 "리그레션 총 342개". 342가 현재 총량이고 120은 작성 당시 값인지, 342 중 릴리스마다 120개를 뽑는 건지 불명. [저자 확인: 답: 여러 프로젝트에서의 리그레션 테스트 케이스의 총 합이 342개라는 것. 특정 프로젝트의 리그레션 테스트 케이스 수를 물어본거임?]
- **답변 5번 스타일**: "10개 정도인 것 같았음" 같은 추측성 답 OK — 집행 세션이 "약 10행" + 추정 표기로 처리함.
- **미확보 확정**: ai-qa-engineer(13·14), api-runner(15~17), design-change(24~26), developer(27) — 수치 없이 진행. 해당 글은 수치 대신 **서사·구조 보강**으로 개선하고, design-change 는 갭 분석 스코프 축소(제목에서 제거)로 확정.
- **release-train(29)**: "파일럿 중이라 모름" → 오히려 좋은 재료. "아직 파일럿 중 — 지표는 N 스프린트 후 후속 글로"라고 미완 과제(S7②)로 쓰면 됨.
