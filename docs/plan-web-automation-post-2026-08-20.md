## 1. 논지 한 줄

**웹 테스트 자동화는 이제 "누가 짜느냐"의 문제가 아니다. 소스와 명세를 텍스트로 쥐고 있으면
에이전틱 AI 가 자동화를 통째로 세운다 — 실측 36건, 사람이 코드를 한 줄도 안 썼다.**

### T1 점검 — 포인트가 하나인가

하나다. 나머지는 그 주장의 **근거·조건·한계**다.

| 요소 | 역할 |
|---|---|
| 관측면이 소스에 있다 | **왜** 되는가 (기전) |
| 15건 3분 30초 · 13건 6분 · 최종 36건 | **얼마나** 되는가 (근거) |
| 세션 간 `@mention` 으로 결함 6건을 자기들끼리 고쳤다 | **어디까지** 되는가 (확장) |
| 빨강 확인 · 잘못된 단언 8건 | **무엇을 지불하는가** (조건·한계) |

### 왜 우리만 쓸 수 있나

"AI 로 테스트 만들었다"는 흔하다. 우리에게 있는 것 셋:

1. **하드웨어와의 대비.** 실물 장비를 실제로 굴리는 팀이라 경계선을 안다.
2. **세션 여러 개를 실제로 붙여 봤다.** 사람이 옮겨 적은 문장 0.
3. **작동 조건을 세어 뒀다.** 8건. 이게 있어야 "정확하게"가 광고가 아니라 관측이 된다.

## 3. 기전 — 관측면

> **관측면** = 테스트가 결과를 읽어낼 수 있는 표면.

| | 관측면 | 결과 |
|---|---|---|
| 웹 | DOM · 네트워크 응답 · 라우팅 | **전부 소스에 텍스트로 있다** |
| 하드웨어 | 일부가 코드 밖(물리)에 있다 | 지폐가 실제로 나왔는지는 소스에 없다 |

**"쉽다"의 정확한 이유가 이것이다.** 웹이라서가 아니라 관측면이 읽히기 때문이다.

여기서 이 글의 반전이 나온다 — 키오스크의 **화면 트랙은 사실 처음부터 순수 웹 테스트였다.**
"실물 장비 프로젝트"라고 부르던 것의 절반이 웹이었는데 그렇게 안 불렀을 뿐이다.
renewal 글의 실측이 뒷받침한다: 실물이 진짜 필요했던 건 **26건 중 1건.**

### 3-1. 같은 이유로 세션 간 대화가 먹힌다

자동화 구축에서 사람 시간을 제일 태우는 건 만드는 일이 아니라 **판정**이다.
빨간 검사 하나 앞에서 답해야 하는 질문은 늘 같다 — *제품이 틀렸나, 명세가 틀렸나, 내 검사가 틀렸나.*

판정 근거가 전부 텍스트라 **세션끼리 읽고 답할 수 있다.** 하드웨어는 근거 일부가 물리 세계에 있어
물어볼 상대가 없다. 사람이 가서 봐야 한다.

**관측면이 텍스트라는 사실 하나가 "만들 수 있다"와 "고칠 수 있다"를 둘 다 낳는다.** 포인트는 여전히 하나다.

## 6. 조건 절의 알맹이 — 빨강 확인

이 글이 독자에게 실제로 넘겨 줄 방법 하나. 여기가 T3("2년 전 나에게 유용했나")를 통과시키는 자리다.

> **검사를 새로 쓰면 일부러 실패시켜 본다.** 실패하지 않으면 그 검사는 아무것도 안 보고 있다.

8건이 전부 한 유형이었다 — **확인하려는 상태와 무관하게 참이 되는 단언.**

| 무엇을 확인한다고 했나 | 왜 눈이 없었나 |
|---|---|
| 관리자 화면이 안 보인다 | 그 화면 제목을 잘못 알았다. **없는 문구의 부재는 영원히 참이다** |
| 보호 라우트로 안 갔다 | 갔다 돌아와도 최종 URL 이 같다 |
| 관리자 화면이 안 그려졌다 | 100ms 만에 사라진다. 폴링이 리다이렉트 뒤에 떨어진다 |

**정점 (C1 · 두 줄이면 충분):**

```
expect(admin 제목).toHaveCount(0)   →  통과
expect(admin 제목).toBeVisible()    →  통과
```

둘 다 통과할 수는 없다. 통과했다는 건 그 단언이 화면을 보고 있지 않았다는 뜻이다.

**부수 교훈** — 빨강 확인을 "반전시켜 실패하나 보기"로만 하면 이걸 못 거른다.
반전이 통과하면 "제품이 그렇구나"보다 **"내 단언에 눈이 없구나"** 를 먼저 의심한다.
